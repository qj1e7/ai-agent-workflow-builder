# Contracts

Every shape that crosses a process boundary, plus recorded example runs. The Portal, the platform-api backend and the agent runtime are built and tested against these files, so they are the shared truth. Nothing in here is written by hand. Each file is generated from pydantic models, and CI fails when a committed file differs from what the models produce.

## Files and owners

| File | Owner | Generated by |
|---|---|---|
| `openapi.json` | platform-api | `platform_api.contracts` |
| `activity-event.schema.json` | platform-api, run monitoring context | `platform_api.contracts` |
| `agent-api.schema.json` | agent-runtime | `agent_runtime.contracts` |
| `fixtures/runs/*.json` | platform-api, run monitoring context | `platform_api.contracts` |
| `fixtures/views/*.json`, `fixtures/approvals/*.json`, `fixtures/internal/*.json`, `fixtures/stubs/*.json` | platform-api, orchestration context | `platform_api.contracts` |
| `fixtures/builder/*.json`, `fixtures/watchlist/*.json` | platform-api, use case builder context | `platform_api.contracts` |
| `fixtures/troubleshooting/*.json` | platform-api, run monitoring context | `platform_api.contracts` |
| `fixtures/agent/*.json` | agent-runtime | `agent_runtime.contracts` |

The owner's models are the source. To change a shape, change the model, regenerate, and commit the model and the files together.

## Regenerate

From the repository root:

```sh
(cd platform-api && uv run python -m platform_api.contracts ../contracts)
(cd agent-runtime && uv run python -m agent_runtime.contracts ../contracts)
```

Each generator deletes and rewrites the fixture folders it owns, so a removed fixture disappears from disk too. CI runs both commands and fails on any diff, then runs `tests/test_contracts.py` in each project, which parses every fixture with that project's models.

## What the fixtures record

Three checks of a Software watchlist that holds one software, LangGraph at our version 1.2.14, each as the full ordered activity event list with realistic timestamps.

- `runs/success.json`. Alice starts the check. The Planner brings in the Version checker, the two agents exchange messages, the checker reads LangGraph's releases, finds 1.2.16 and 1.2.15 newer than 1.2.14, and an upgrade ticket in MOCK is proposed. The approval is requested and announced in the Teams channel "CODESparks Ops". About six minutes later Bob approves, the act leg runs, the ticket is written as MOCK-142, and the run succeeds.
- `runs/failure.json`. GitHub answers 503 three times, the Version checker gives up on the one software it has, and the run fails with reason `AgentError`, retryable.
- `runs/rejected.json`. The same work leg, then Bob declines.

`views/` holds the `GET /api/v1/runs/{run_id}` answer for each run at the end and at the approval pause (for the failure, while the agents are working). `approvals/` holds `GET /api/v1/approvals/apr_01JB8` as Alice sees it (refused, own work) and as Bob sees it (can decide), plus one recorded decision and one refusal body. `agent/` holds the Agent API task request, a finished result, a failed result (a watchlist check that could read none of its software also carries each one's finding, with its own reason), one callback post and the agent cards, and the four tools (`tools.json`), a card task (`card-task-request.json`, `card-task-finished.json`), a draft (`card-draft-request.json`, `card-drafted.json`), a Planner choice (`planner-choose-request.json`, `planner-chosen.json`), what the Planner understood of a task (`planner-understand-request.json`, `planner-understood.json`, `planner-watchlist.json`), and a watchlist check of three software (one behind, one up to date, one that cannot be read) as `watchlist-task-request.json` and `watchlist-task-finished.json`. Apart from the three-software result, the agent events inside the results are the same events, with the same timestamps, as the agent-actor events in `runs/`. `troubleshooting/failure.json` is the AI troubleshooter's answer for the failed run.

`builder/templates.json` lists the two templates that remain, neither offered to be built by hand: the Software watchlist, which the Software page makes, and agent cards, which the Builder page makes. `builder/use-case.json` is the watchlist as a use case. `builder/suggest.json` is the answer of `POST /api/v1/use-cases/suggest`, which names no template now.

### Pausing, deleting and drafts

Every use case view says whether the workflow is `on` or `paused` (`state`), and when it next runs on its own (`next_run_at`). `next_run_at` is null while it is paused, and for a workflow with no schedule. Operators pause, resume, delete and restore with `POST /api/v1/use-cases/{use_case_id}/pause`, `POST .../resume`, `DELETE /api/v1/use-cases/{use_case_id}` and `POST .../restore`. Pause, resume and restore answer the use case view (`builder/use-case.paused.json` is the watchlist paused). The delete answers `builder/use-case.deleted.json`: when it was deleted and the time until which a restore puts it back, a day later. Each answers the same when repeated. A paused workflow starts no run, on its schedule or by hand (409). A deleted one leaves `GET /api/v1/use-cases`, answers 404 to a read, a start, a pause or a resume, and keeps its runs, so a run waiting for a yes can still be decided. A restore after the day answers 410. The Software watchlist can be paused but not deleted (409). `GET /api/v1/watchlist` carries the same `state`, and while the watchlist is paused its `schedule.next_at` is null (`watchlist/paused.json`).

`PUT /api/v1/drafts/{draft_id}` saves a New workflow draft for the signed-in Operator (`builder/draft.in.json`): the step it was saved at, 1 to 4, and the form as opaque JSON of at most 32 KB. The Portal picks the draft id. `GET /api/v1/drafts` lists only the caller's own drafts, the last saved first (`builder/drafts.json`), and `DELETE /api/v1/drafts/{draft_id}` removes one of theirs (204). Someone else's draft id is a 404. An Operator keeps at most 20 drafts.

Text the API is sent never holds a NUL character. A request body with one answers 422 naming the field, a path with one answers 404, and a query parameter with one answers 422 naming it.

### The software watchlist

`watchlist/` records the Software page's API ([ADR 0019](../docs/adr/0019-watch-software-in-one-list-with-one-approval-per-check.md)). `none.json` is `GET /api/v1/watchlist` before any software is added (`watchlist: null`). `statuses.json` is the view with one row in each status, already in the order the page shows them: cannot check, behind, awaiting approval, ticket open, not checked, then up to date, and by name within one status. Each row carries our version and where it came from (`given` by the Operator, `first_check`, or `ticket_done` with the ticket key), the newest version, when it was read (`newest_read_at`) and when the row was last checked, the problem sentence when the check could not read it (the row then keeps the newest version an earlier check read), the open ticket, and the approval to decide. `empty.json` is the view after the last software was removed, which `POST /api/v1/watchlist/software` and `DELETE /api/v1/watchlist/software/{software_id}` also answer. `add-software.json` is the body of the add. `POST /api/v1/watchlist/software/{software_id}/restore` is the page's Undo. It lists removed software again with the same id, our version as typed, and who added it and when, so what the platform learned about it comes back. It works for a day after the removal, as a workflow's Restore does, and a later try is a 410. Restoring software that is on the list answers the view unchanged, an id that was never listed is a 404, and a repository added again since is a 409.

The schedule ([ADR 0020](../docs/adr/0020-our-api-keeps-schedules-and-one-n8n-workflow-asks-what-is-due.md)) is the `schedule` field of the view: `day` (`every_day` or a weekday name), `at` (`HH:MM` on a 5-minute step), `time_zone` (`Asia/Singapore`), the schedule owner (`owner` is the user id, `owner_name` the name to show), `saved_at`, and `next_at`, the next time a check starts, or null while the watchlist is paused. `schedule` is null when the schedule is off. The first add of software saves Monday 09:00 for the person who added it. `PUT /api/v1/watchlist/schedule` takes `watchlist/schedule.in.json`, makes the caller the schedule owner, and answers the view (`schedule.saved.json`). `DELETE /api/v1/watchlist/schedule` turns it off and answers the view with `schedule: null` (`schedule.off.json`). Both are Operator routes, and both answer 404 until the watchlist exists. A bad day or time is a 422.

A scheduled check is started by the schedule owner, so `started_by` is the owner, who cannot approve it. Every run view and `run_created` event says how it started: `trigger` is `person` or `schedule`. `views/scheduled.pending.json` is a scheduled run, and its `run_created` summary reads "Alice's schedule started a check of Software watchlist." The `schedule_tick` workflow asks `POST /internal/v1/schedules/tick` (step key, not a signed-in route) every 5 minutes; it answers the runs it started (`internal/tick.started.json`, or `internal/tick.nothing-due.json`).

`runs/watchlist.json` is one recorded check, which the Portal's demo replays. `watchlist/before-check.json` is the watchlist just before it: six software with the results of Monday's scheduled check, and Alice's schedule for Mondays at 9:00. On Friday Alice starts a check by hand. The Version checker reads each source in list order: n8n is up to date, LangGraph, Redis and PostgreSQL are behind, FastAPI's source answers 404 and the checker carries on, and Terraform, added without a version, gets its starting point. The agents propose three upgrade tickets in one proposal (`views/watchlist.awaiting_approval.json`), Bob approves them with one decision, and they are written as MOCK-143, MOCK-144 and MOCK-145.

`stubs/mock-jira-tickets.json` shows a practice Jira ticket with its `status` (`To Do` or `Done`) and `done_at`. `stubs/mock-jira-ticket.done.json` is the answer of `POST /api/v1/mock-jira/tickets/{key}/done`, which an Operator uses as a person would in Jira; marking a Done ticket again answers the same. The watchlist moves our version to the version a Done ticket named.

## Agent cards

An agent card is data: a name, a purpose, inputs and numbered blocks, each block naming at most one of four tools (`github.read_releases`, `jira.search`, `jira.read_ticket`, `jira.create_ticket`). [ADR 0023](../docs/adr/0023-agents-are-cards-the-model-drafts-and-use-only-tools-we-build.md) has the decision. The agent runtime serves `GET /v1/tools`, `POST /v1/cards/draft`, `POST /v1/planner/choose`, and runs card tasks (`inputs.kind` is `cards`) through `POST /v1/tasks`.

- A running agent is offered only its card's tools. A write tool takes `title` and `body` and never a target. It only records a proposal: `kind` is the tool id and `subject` is the card id.
- Each tool call is a step pair. `step` is the tool id with `_` for `.`, such as `jira_search`. A finished read has one list of text in `result` for the live view (`tags`, or ticket keys with titles).
- Jira reads call the platform's practice Jira at `PRACTICE_JIRA_URL` with the task's callback token. A search or a read can only reach the Jira project on the card.
- A task has 50 seconds and each agent 8 model turns.

## What the Planner understood

Before a workflow is set up, the Planner reads the Operator's task back in four parts: `schedule` (when it runs), `look_for` (what to look for), `do` (what to do with it) and `where` (where the result goes). Each row is `understood`, `changed` (the Planner read something into the words, and the note says what the task said), `missing` (the task does not say, so `text` is empty) or `cant_do` (no tool does it, and the note says why, even when `text` is empty). There is one schedule row first, then at least one row of each other kind, at most 8 rows.

The agent runtime serves `POST /v1/planner/understand` (`agent/planner-understand-request.json`). The request carries the task, the model, and `jira_projects`, the keys of the Jira projects the platform can see: the practice Jira's home project MOCK and each project a ticket was written to. It answers the rows (`agent/planner-understood.json`), or `status: "watchlist"` with the word in the task that made it think the task is about software versions, releases or vulnerabilities, and the software when the task names one (`agent/planner-watchlist.json`), or a model problem. Two rules hold whatever the model says. First, the model never writes a row. For each part it names one ability from the fixed table in `agent-runtime/src/agent_runtime/abilities.py`, with that ability's parameters, and the platform writes the row's `text` itself, in its own words. The table holds what the platform can do: run on a schedule (`every`, `at`, `on`), read Jira tickets (a kind of ticket, a project, who they are assigned to, what they are about, when they were closed or created, days with no update), sum up what it finds (in the run's report), check software for new releases, and create a Jira ticket after a yes (in a Jira project, by key or by name). A part that names no ability in the table, an ability that does not fit the part, or a parameter that does not check out is `cant_do`. Each parameter is a short, checked value. A day, a time or a period is one of a fixed set of words. A status sits beside the tickets it describes ("open bug tickets"). A Jira key is a key the task wrote, in its own case, and never the name of another system (TEAMS, SLACK). A project or board name is followed by "project" or "board" in the task, and is never just the name of another system ("the Teams project"). A value taken from the task's words (a kind of ticket, a name, a topic) is plain text of a few words that the task holds where such a value sits, as the task wrote it: a kind of ticket right before "tickets", after a word such as "find", "the" or "open"; a topic after "about", "for", "listing", "where" or "find"; a person after "assigned to"; what to sum up by after "by" or "for each"; the software next to a word for releases ("Check LangGraph for new releases"). When the model's copy of the part (`said`) holds the value, that copy is where it must sit. It never starts a clause (after "and", "then", "please", a comma and the like, and a topic not after "that", "which", "who" or "to"), joins one on, points back at what was found ("them", "the rest"), names a ticket, holds a search query (`=`, `~`, brackets, `AND`, `ORDER BY`), holds a word for a write in any form ("close", "closing", "closed", "get rid of", "sum up by deleting"), or names another system. A topic or a kind of ticket may name another system when it describes Jira tickets: tickets about the GitLab issue from last week stay understood. The lists of write words and other systems sit beside the table, and they are read after NFKC with look-alike letters, accents and hidden characters folded, so "clоse" with a Cyrillic letter and "c̶l̶o̶s̶e̶" count. A part whose own words in the task give an order to change something, a search or a step that names another system and no tickets, and a `where` part that names a place outside Jira are `cant_do` however the parameters are filled in. A parameter the ability does not take must be empty, unless it is a key, a number or one of the fixed words. So a write tucked into a ticket's topic, a place outside Jira put in as a project, or an order after the schedule ("Every Friday, approve pending access requests") is `cant_do`. A topic is shown in quote marks, as the task's words, and a search whose source is another system ("who has admin access in GitLab") is `cant_do`. A row is `understood` only when each fixed value it shows (a day, a time, a number of days, a period, how to sum up, and that a new ticket lists what was found) is the task's own and its Jira project is one of `jira_projects`. Otherwise it is `changed`, and the note asks the Operator to check: "I can't check that ACCESS is a Jira project." when the request has no list, "I can't find a Jira project OPS." when the list lacks it, and "I can't check that the Access Review project is in Jira." for a project named by name, since the practice Jira lists keys only. The model's own words are never shown as it wrote them. A `cant_do` row shows the task's own words for the part: the model's copy when the task holds it, otherwise the longest value of the row the task holds, otherwise "This part of your task". A `changed` row's note quotes the task's words only when they hold no write, and name another system only when they also say tickets. Every note is the platform's: a `missing` row says which part the task did not say, a `cant_do` row says "I can't do this yet." (or "I can't read GitLab yet.", or "I can't put results there yet.") and what the platform can do, and a `changed` row says what it read in or could not check and asks the Operator to check. Text is read as NFKC, without hidden characters, and words in any script, with their combining marks, are kept whole. Second, the watchlist word must be in the task and be a form of version, release, upgrade, patch or vulnerability, the words the prompt names. The answer shows the task's own word: the model's word when the task has it, otherwise the first other form of the same word, so "versioned" never stands in for "version". The software must be a whole word of the task, so "Go" never matches "Google". Otherwise the answer is unusable, and the platform answers the starters. The model gets 8 seconds.

The Portal asks `POST /api/v1/builder/understand` with `{text}`, as an Operator (anyone else gets 403). The answer's `answer` field says which of three shapes it is: `rows` (`builder/understand.rows.json`), `watchlist` with the word, the software and the Planner's sentence (`builder/understand.watchlist.json`), or `starters`, the fixed starter workflows with a plain `message` saying why (`builder/understand.starters.json`). The starters come back when no AI model is connected, when the model fails or its answer does not parse, and when there is no answer within 10 seconds. The platform logs why. A starter carries the `task` to start from, or `opens: "software_watchlist"`. The route never saves or writes anything.

## The activity event

Every event has `run_id`, `seq` (gapless from 1 per run), `ts`, `actor {kind, id, display}`, `kind`, `summary` and `data`. `summary` is plain English written by whoever emitted the event, so the Portal never composes English from `data`. `kind` selects the shape of `data`. The schema is a `oneOf` over the kinds, so a TypeScript generator produces a discriminated union.

| Kind | Actor | Data |
|---|---|---|
| `run_created` | user | `use_case_id`, `use_case_version`, `started_by`, `trigger` (`person` or `schedule`) |
| `leg_dispatched` | platform | `leg`, `attempt` |
| `step_started`, `step_retried` | workflow | `step`, `n8n_execution_id`, `try_number` |
| `step_finished` | workflow | `step`, `n8n_execution_id`, `try_number`, `outcome`, `detail` |
| `agent_joined` | agent (the Planner) | `agent {id, display}`, `reason` |
| `agent_step_started` | agent | `step` |
| `agent_step_finished` | agent | `step`, `result` (free-form object) |
| `agent_failed` | agent | `step`, `error_type`, `message`, `retryable` |
| `agent_message` | agent | `speaker {id, display}`, `addressee` (`{kind: "agent", id, display}` or `{kind: "room"}`), `text` |
| `write_action_proposed` | agent | `proposal_id`, `digest`, `actions[] {connector, operation, line}` |
| `approval_requested` | platform | `approval_id`, `steps[] {index, label, status, decided_by, decided_at}`, `link` |
| `approval_announced` | platform | `approval_id`, `channel`, `link` |
| `approval_announce_failed` | platform | `approval_id`, `channel`, `message` |
| `approval_decided` | user | `approval_id`, `step`, `verdict`, `by` |
| `write_action_denied` | safety_checker | `reason`, `detail` |
| `write_action_done` | platform | `connector`, `operation`, `external_reference`, `approved_by[]` |
| `run_succeeded` | platform | `outcome` (`written` or `nothing_to_write`) |
| `run_rejected` | platform | `by`, `step` |
| `run_failed` | platform | `stage`, `reason`, `retryable`, `message` |
| `run_retried` | user | `leg`, `attempt` |

`run_failed.reason` is one of `AgentError`, `WorkflowNodeError`, `TimedOut`, `DispatchFailed`, `WriteFailed`, `SafetyDenied`, `UnboundIntent`, `OutOfOrderStep`. The AI troubleshooter has one rule per reason.

## Sign-in

platform-api has two sign-in modes. `AUTH_MODE` picks one at startup. The contract is the same in both, except that local mode adds `GET /api/v1/dev/users`.

Local mode (`AUTH_MODE=dev`) starts only with a `PUBLIC_BASE_URL` on `localhost` or `127.0.0.1`. Portal routes then read `X-Dev-User`, one of the ids from `GET /api/v1/dev/users`: `alice` (Operator and Approver), `bob` (Approver), `carol` (Operator). Alice starts the fixture runs, so she is refused with `own_work` when she tries to approve them.

Real sign-in (`AUTH_MODE=oidc`) reads an OpenID Connect access token from the `Authorization: Bearer` header and ignores `X-Dev-User`. platform-api checks the token's signature against the identity provider's published keys (RS256 or ES256 only), then its issuer, its audience and its times. The person's id is the `oid` claim, or `sub` when there is no `oid`. Their roles come from the `roles` claim, where `Operator` and `Approver` are the only values that count. [ADR 0018](../docs/adr/0018-sign-in-with-openid-connect.md) explains the choice.

`openapi.json` declares both modes as security schemes: `DevUser`, an API key in the `X-Dev-User` header, and `OidcBearer`, an HTTP bearer token in JWT format. Every route that reads the signed-in user lists both. That means one or the other signs the request in, depending on the mode. A client that reads the contract sees which routes need a signed-in user.

`GET /api/v1/me` answers who the platform takes the caller to be: `id`, `display` and `roles`. The Portal shows that instead of reading the token itself.

Every error the API sends from its own code has the body `{"detail": "..."}`, and each route declares the error statuses it can answer: 401 without a signed-in user, 403 when the user's role does not allow the route, 404 for an unknown id, 409 when the state of the run or approval does not allow the action, and 503 on every signed-in route when the identity provider's keys cannot be fetched, with a `Retry-After` header. In real sign-in a 401 also carries `WWW-Authenticate: Bearer`. The two other error bodies are the refusal on a decision (`RefusalOut`) and the try-again-later answer of the step route (`RetryLater`). Request validation answers 422 in FastAPI's own shape.

## The agent callback

The task request gives the agent `callback {url, token}`. The agent posts each event to `url` with the token in the `X-Callback-Token` header, never in the URL, because query strings end up in access logs. The handler must compare the token in constant time, bind it to the run and task, and give it an expiry.
