# Contracts

Every shape that crosses a process boundary, plus recorded example runs. The Portal, the platform-api backend and the agent runtime are built and tested against these files, so they are the shared truth. Nothing in here is written by hand. Each file is generated from pydantic models, and CI fails when a committed file differs from what the models produce.

## Files and owners

| File | Owner | Generated by |
|---|---|---|
| `openapi.json` | platform-api | `platform_api.contracts` |
| `activity-event.schema.json` | platform-api, run monitoring context | `platform_api.contracts` |
| `agent-api.schema.json` | agent-runtime | `agent_runtime.contracts` |
| `fixtures/runs/*.json` | platform-api, run monitoring context | `platform_api.contracts` |
| `fixtures/views/*.json`, `fixtures/approvals/*.json`, `fixtures/internal/*.json`, `fixtures/stubs/*.json` | platform-api, orchestration context | `platform_api.contracts` |
| `fixtures/builder/*.json`, `fixtures/watchlist/*.json`, `fixtures/planner/*.json` | platform-api, use case builder context | `platform_api.contracts` |
| `fixtures/troubleshooting/*.json` | platform-api, run monitoring context | `platform_api.contracts` |
| `fixtures/agent/*.json` | agent-runtime | `agent_runtime.contracts` |

The owner's models are the source. To change a shape, change the model, regenerate, and commit the model and the files together.

## Regenerate

From the repository root:

```sh
(cd platform-api && uv run python -m platform_api.contracts ../contracts)
(cd agent-runtime && uv run python -m agent_runtime.contracts ../contracts)
```

`fixtures/planner/capabilities*.json` are made from the runtime's `fixtures/agent/capabilities.json`, so after a change to the registry run the runtime's generator first.

Each generator deletes and rewrites the fixture folders it owns, so a removed fixture disappears from disk too. CI runs both commands and fails on any diff, then runs `tests/test_contracts.py` in each project, which parses every fixture with that project's models.

## What the fixtures record

Three checks of a Software watchlist that holds one software, LangGraph at our version 1.2.14, each as the full ordered activity event list with realistic timestamps.

- `runs/success.json`. Alice starts the check. The Planner brings in the Version checker, the two agents exchange messages, the checker reads LangGraph's releases, finds 1.2.16 and 1.2.15 newer than 1.2.14, and an upgrade ticket in MOCK is proposed. The approval is requested and announced in the Teams channel "CODESparks Ops". About six minutes later Bob approves, the act leg runs, the ticket is written as MOCK-142, and the run succeeds.
- `runs/failure.json`. GitHub answers 503 three times, the Version checker gives up on the one software it has, and the run fails with reason `AgentError`, retryable.
- `runs/rejected.json`. The same work leg, then Bob declines.

`views/` holds the `GET /api/v1/runs/{run_id}` answer for each run at the end and at the approval pause (for the failure, while the agents are working). A run waiting for a yes says whether the signed-in person can decide it now (`you_can_decide`), by the same rule as its approval, in this answer and in each item of `GET /api/v1/runs`. The waiting views are as Bob sees them, so it is true. `approvals/` holds `GET /api/v1/approvals/apr_01JB8` as Alice sees it (refused, own work) and as Bob sees it (can decide), plus one recorded decision and one refusal body. Both views also name the workflow (`use_case_id`, `use_case_name`), who set it up (`owner`), who started the run and how (`started_by`, `trigger`), who retried it (`retried_by`), and what the agents found (`found`). Each Jira action's `target` names the Jira site it goes to beside the project, `practice` or `jira:` and a fingerprint of the address, and the digest covers it (ADR 0041). Each action in an approval view also says where it goes in words (`site_name`): "the practice Jira", the host of the Jira set up now, or "a Jira that is no longer set up" when the site changed since, so the safety checker would refuse the write with `target_changed`. `agent/` holds the Agent API task request, a finished result, a failed result (a watchlist check that could read none of its software also carries each one's finding, with its own reason), one callback post and the agent cards, the four tools (`tools.json`), the capability registry with the day-one examples (`capabilities.json`), a card task (`card-task-request.json`, `card-task-finished.json`), a draft (`card-draft-request.json`, `card-drafted.json`), a Planner choice (`planner-choose-request.json`, `planner-chosen.json`), what the Planner understood of a task (`planner-understand-request.json`, `planner-understood.json`, `planner-watchlist.json`), the Planner's one answer to a request typed on Home (`planner-answer-request.json`, then `planner-answered-card.json`, `planner-answered-cant.json`, `planner-answered-watchlist.json` and `planner-answered-refused.json`), and a watchlist check of three software (one behind, one up to date, one that cannot be read) as `watchlist-task-request.json` and `watchlist-task-finished.json`. Apart from the three-software result, the agent events inside the results are the same events, with the same timestamps, as the agent-actor events in `runs/`. `troubleshooting/failure.json` is the AI troubleshooter's answer for the failed run, with its four answers (`answers`: what happened, what was affected, whether a retry is safe and whether it asks for a new yes, and what to do next).

`builder/templates.json` lists the two templates that remain, neither offered to be built by hand: the Software watchlist, which the Software page makes, and agent cards, which the Builder page makes. `builder/use-case.json` is the watchlist as a use case. `builder/suggest.json` is the answer of `POST /api/v1/use-cases/suggest`, which names no template now.

### Pausing, deleting and drafts

Every use case view says whether the workflow is `on` or `paused` (`state`), when it next runs on its own (`next_run_at`), and its schedule (`schedule`: `day`, `at`, `time_zone`, the schedule owner's name `owner_name`, and `held`). `next_run_at` is null while it is paused, while its schedule is held (below), and for a workflow with no schedule. `schedule` stays while it is paused or held, and is null for a workflow with no schedule. `held` names why a held schedule starts no run, with the same reasons as the watchlist's schedule (below), and is null while the owner can run it. `builder/use-case.held.json` is the watchlist after Alice has left the People list. Operators pause, resume, delete and restore with `POST /api/v1/use-cases/{use_case_id}/pause`, `POST .../resume`, `DELETE /api/v1/use-cases/{use_case_id}` and `POST .../restore`. Pause, resume and restore answer the use case view (`builder/use-case.paused.json` is the watchlist paused). The delete answers `builder/use-case.deleted.json`: when it was deleted and the time until which a restore puts it back, a day later. Each answers the same when repeated. A paused workflow starts no run, on its schedule or by hand (409). A deleted one leaves `GET /api/v1/use-cases`, answers 404 to a read, a start, a pause or a resume, and keeps its runs, so a run waiting for a yes can still be decided. A restore after the day answers 410. The Software watchlist can be paused but not deleted (409). `GET /api/v1/watchlist` carries the same `state`, and while the watchlist is paused its `schedule.next_at` is null (`watchlist/paused.json`).

`PUT /api/v1/drafts/{draft_id}` saves a draft of a set-up card for the signed-in Operator (`builder/draft.in.json`): the step it was saved at, 1 to 4 (optional, a draft saved from a Planner card has none), and the form as opaque JSON of at most 32 KB. The Portal picks the draft id. `GET /api/v1/drafts` lists only the caller's own drafts, the last saved first (`builder/drafts.json`), and `DELETE /api/v1/drafts/{draft_id}` removes one of theirs (204). Someone else's draft id is a 404. An Operator keeps at most 20 drafts.

Text the API is sent never holds a NUL character. A request body with one answers 422 naming the field, a path with one answers 404, and a query parameter with one answers 422 naming it.

### Connections

`GET /api/v1/settings/connections` lists Jira, GitHub, Teams and the AI model, each with its last check (`settings/connections.json`): `state` (`working`, `needs_attention`, `not_answering`, `not_set_up` or `not_checked`), when the result shown was found (`checked_at`) and when it last worked, a plain `problem` and one `fix`, the key's last two characters when it has one, and `expires_at` only when the system says so. A result belongs to the address and key that found it. After a change of either one, the connection has no history: `checked_at` and `last_ok_at` are null until something is tried with the new ones, and a real Teams channel reads `not_checked` until its first post (`settings/connection.not_checked.json`). `you_can_check` is true for an Operator, and only an Operator may `POST /api/v1/settings/connections/{connection}/check`, which answers that one connection (`settings/connection.checked.json`). A check only reads, so Check now on a real Teams channel answers what its last post found. The schedule tick checks a working connection at most once an hour, and one that does not work, or waits for a second reading, on every tick. It changes a state only when two checks in a row agree, and a Teams channel's posts follow the same rule. The AI model is read from the model settings on every request, so Settings, Connections and Home agree, and its `checked_at` and `last_ok_at` are null. `GET /api/v1/home` carries `connections` for an Operator: the ones that do not work and the keys that run out within 14 days, as the last check left them, each with its `checked_at`. Home never starts a check.

### The software watchlist

`watchlist/` records the Software page's API ([ADR 0019](../docs/adr/0019-watch-software-in-one-list-with-one-approval-per-check.md)). `none.json` is `GET /api/v1/watchlist` before any software is added (`watchlist: null`). `statuses.json` is the view with one row in each status, already in the order the page shows them: cannot check, behind, awaiting approval, ticket open, not checked, then up to date, and by name within one status. Each row carries our version and where it came from (`given` by the Operator, `first_check`, or `ticket_done` with the ticket key, which is null when that ticket is not in the Jira set up now), the newest version, when it was read (`newest_read_at`) and when the row was last checked, the problem sentence when the check could not read it (the row then keeps the newest version an earlier check read), the ticket open in the Jira set up now (ADR 0041), and the approval to decide. `empty.json` is the view after the last software was removed, which `POST /api/v1/watchlist/software` and `DELETE /api/v1/watchlist/software/{software_id}` also answer. `add-software.json` is the body of the add. `POST /api/v1/watchlist/software/{software_id}/restore` is the page's Undo. It lists removed software again with the same id, our version as typed, and who added it and when, so what the platform learned about it comes back. It works for a day after the removal, as a workflow's Restore does, and a later try is a 410. Restoring software that is on the list answers the view unchanged, an id that was never listed is a 404, and a repository added again since is a 409.

The agent runtime serves `POST /v1/planner/answer` with `{task, model}` (`agent/planner-answer-request.json`), the Planner's one answer to a request typed on Home (ADR 0037). It answers `status: "answered"` with one `answer`, told apart by `kind`, or a model problem. The kinds are `setup_card` (a name and the rows), `part` (the rows the platform can do and `cant`, the parts it can't), `cant` (the parts it can't do and, when the rest checks out, an `alternative`: a card or a watchlist row), `watchlist` (the task's own word, the software, and `also`, the rest of a request that also asks for a workflow), `which_software`, `refused` (a request to skip a yes, with `said`, the words that asked to, and `rest`, the request without them), `check_workflows` and `why_stopped` (with `workflow_words`, the words of the request that name one workflow, which the platform matches), `needs_me` and `abilities`. Each part the platform can't do says what it needs: `new_tool` when it is in a system the platform already reaches, such as Jira or GitHub, so the team decides, or `new_system`, with the system it names. The model reads the request into closed structures (the ticket search the platform runs, the new ticket, the project it goes in, the schedule, and whose yes the request asks to skip), and code decides the kind from them, in this order: refused, watchlist, a question about the person's workflows, then the rows, then abilities when nothing was read. Code renders every row from the structures, so a card claims only what the platform will run, and a filter the request never framed is dropped. Each structure explains the request's words only where its quote stands, and every content word nothing explains comes back to the person in their own words: as a refusal when it names a yes, another person, a role or a group in a request that writes, else as a part the platform can't do. A request that asks to skip a yes is refused by a word rule before the model is asked, and after it by the model's answer to the skip question, which code never overrules: it only ever refuses more. The model gets 8 seconds. The fixtures are a card for the demo task, a can't with the email task and its alternative, the watchlist row for the release task, and a refusal.

`POST /api/v1/watchlist/software/{software_id}/address` is the page's Use the new address. Each check records the `full_name` GitHub answers for the saved repository (`GET /repos/{owner}/{name}`), and a row carries `moved_to` when that name differs from the saved one by more than case, and `not_found` when GitHub answered 404 for it. The body `{"repo": ...}` names the address the person saw, and the route replaces the saved repository with it only when it is the one GitHub reported: otherwise it is a 409. It saves a new version of the list, so every later check reads the new address, and writes nothing outside our own list. Asking again for the address already saved answers the view unchanged. `POST .../address/undo` takes the address to go back to, which must be one the software had before, and works for a day after the switch (410 later, 409 when the list now watches that address). Both are Operator routes, and a software that is not listed is a 404. `watchlist/moved.json` is a list with one renamed repository (FastAPI, saved as tiangolo/fastapi) and one GitHub cannot find (LangServe), which has `not_found` and no `moved_to`, so nothing is offered for it. A finding from the agent runtime carries `full_name` and `not_found` for the same two facts.

The schedule ([ADR 0020](../docs/adr/0020-our-api-keeps-schedules-and-one-n8n-workflow-asks-what-is-due.md)) is the `schedule` field of the view: `day` (`every_day`, `weekdays` for Monday to Friday, or a weekday name), `at` (`HH:MM` on a 5-minute step), `time_zone` (`Asia/Singapore`), the schedule owner (`owner` is the user id, `owner_name` the name to show), `saved_at`, and `next_at`, the next time a check starts, or null while the watchlist is paused or the schedule is held. A schedule is held while its owner has left the People list (`held` is `owner_removed`) or is no longer an Operator (`owner_not_an_operator`): it starts no check, and the tick uses each slot up as it does for a paused workflow. It starts again when the owner is an Operator again, or when another Operator saves it and so becomes the owner (`watchlist/schedule.held.json`). `held` is null, or left out, while the owner can run it. `schedule` is null when the schedule is off. The first add of software saves Monday 09:00 for the person who added it. `PUT /api/v1/watchlist/schedule` takes `watchlist/schedule.in.json`, makes the caller the schedule owner, and answers the view (`schedule.saved.json`). `DELETE /api/v1/watchlist/schedule` turns it off and answers the view with `schedule: null` (`schedule.off.json`). Both are Operator routes, and both answer 404 until the watchlist exists. A bad day or time is a 422.

A scheduled check is started by the schedule owner, with the roles they hold on the People list at that moment, so `started_by` is the owner, who cannot approve it. Every run view and `run_created` event says how it started: `trigger` is `person` or `schedule`. `views/scheduled.pending.json` is a scheduled run, and its `run_created` summary reads "Alice's schedule started a check of Software watchlist." The `schedule_tick` workflow asks `POST /internal/v1/schedules/tick` (step key, not a signed-in route) every 5 minutes; it answers the runs it started (`internal/tick.started.json`, or `internal/tick.nothing-due.json`).

`runs/watchlist.json` is one recorded check, which the Portal's demo replays. `watchlist/before-check.json` is the watchlist just before it: six software with the results of Monday's scheduled check, and Alice's schedule for Mondays at 9:00. On Friday Alice starts a check by hand. The Version checker reads each source in list order: n8n is up to date, LangGraph, Redis and PostgreSQL are behind, FastAPI's source answers 404 and the checker carries on, and Terraform, added without a version, gets its starting point. The agents propose three upgrade tickets in one proposal (`views/watchlist.awaiting_approval.json`), Bob approves them with one decision, and they are written as MOCK-143, MOCK-144 and MOCK-145.

The agent runtime's `SoftwareToCheck.from_first_check` is true when `our_version` is only the newest release an earlier first check read, and the platform sets it from the same fact the watchlist view shows as `compared_from`. The ticket then reads "Upgrade Moby to docker-v29.9.3" with "newer than v25.0.18, the newest the first check read", and never calls that version "our version". The platform's `review()` expects exactly that title, so the approval, the ticket and the page say the same thing. A version someone gave, or one a Done ticket moved, keeps "from X to Y" and "our version".

`stubs/teams-messages.json` is the practice Teams copy as the success run asks for a yes, and `stubs/teams-messages.decided.json` the same message after Bob's yes. Each message carries the `card` a real Teams channel gets ([ADR 0036](../docs/adr/0036-the-approval-request-goes-to-teams-as-an-adaptive-card-that-opens-our-approval-page.md)): an Adaptive Card 1.4 made only of `RichTextBlock` with `TextRun`, `TextBlock` and one `Action.OpenUrl` to the approval page's absolute address. The line after the workflow names who set it up ("Set up by Alice"). Text the platform did not write is only ever in a `TextRun`, which has no markdown, and its web addresses and markdown links are broken (`https[:]//example[.]com`), so none can become a link. Once the request is decided, the card's first block (`id: "outcome"`) says who approved or declined. `card` is null only for a message posted before cards. `text` is the same request in one plain sentence.

`schemas/adaptive-card-1.5.json` is a copy of the Adaptive Card schema from <https://adaptivecards.io/schemas/adaptive-card.json> (it redirects to adaptivecards.microsoft.com), taken on 1 Nov 2026, SHA-256 `12815f7a1f4408d533a5b97140264f840374c6a3bd51533aaa1c8cf05a9fa20e`. Its newest parts are version 1.5. platform-api's `tests/test_teams_card.py` checks every card, and every card in these fixtures, against it, and never fetches it. It is the one file in `contracts/` not generated from our models. To update it, download it again and update the checksum here.

`stubs/mock-jira-tickets.json` shows a practice Jira ticket with its `status` (`To Do` or `Done`) and `done_at`. `stubs/mock-jira-ticket.done.json` is the answer of `POST /api/v1/mock-jira/tickets/{key}/done`, which an Operator uses as a person would in Jira; marking a Done ticket again answers the same. The watchlist moves our version to the version a Done ticket named.

## Agent cards

An agent card is data: a name, a purpose, inputs and numbered blocks, each block naming at most one of four tools (`github.read_releases`, `jira.search`, `jira.read_ticket`, `jira.create_ticket`). [ADR 0023](../docs/adr/0023-agents-are-cards-the-model-drafts-and-use-only-tools-we-build.md) has the decision. The agent runtime serves `GET /v1/tools`, `POST /v1/cards/draft`, `POST /v1/planner/choose`, and runs card tasks (`inputs.kind` is `cards`) through `POST /v1/tasks`.

- A running agent is offered only its card's tools. A write tool takes `title` and `body` and never a target. It only records a proposal: `kind` is the tool id and `subject` is the card id.
- Each tool call is a step pair. `step` is the tool id with `_` for `.`, such as `jira_search`. A finished read has one list of text in `result` for the live view (`tags`, or ticket keys with titles).
- Jira reads call the platform at `PLATFORM_JIRA_URL`, `/internal/v1/runs/{run_id}/jira/tickets`, with the task's callback token. The platform answers from the practice Jira or a real one (ADR 0035), so the agent never holds a Jira key. `PLATFORM_JIRA_URL` must be one of `CALLBACK_ALLOWED_ORIGINS`. A search or a read can only reach the Jira project on the card.
- A task has 50 seconds and each agent 8 model turns.

## The GitHub connection check

The agent runtime serves `POST /v1/connections/github/check` (behind the agent key). It asks GitHub's rate limit endpoint, which does not count against the limit, and answers `status: "working"` with `using_token` and, when GitHub sends a token end date, `expires_at` (`agent/github-check-working.json`, `agent/github-check-expiring.json`), or `status: "problem"` with `reason` (`token_refused`, `unreachable`, `unexpected_answer`) and a plain `message` that never holds the token (`agent/github-check-refused.json`). With no token the check reads GitHub anonymously and passes. platform-api keeps each result (plan item N18).

The agent runtime serves `POST /v1/software/find` with `{name, tag_pattern}` (`agent/software-find-request.json`). It looks the name up in a reviewed list of known GitHub projects, never through a model, and asks GitHub about each match before offering it. The answer's `status` is `found` with one or more matches (`agent/software-found.json`, Terraform's two), `not_known` when the list has no such name or GitHub found none of its projects, or `not_checked` when GitHub could not say, in which case no project is offered and the message says what went wrong. Each match carries the project at the address GitHub gives it now, what it is, where the guess came from, and whether it has a release that `tag_pattern` counts (`published` or `none`) with the newest such tag. `tag_pattern` is the watch's own tag rule, so the finder and the watch agree on which releases count. The builder's `POST /api/v1/watchlist/find` sends the watchlist's rule (`SOFTWARE_WATCHLIST.tag_pattern`), which counts a plain or v-prefixed version and the main-product tags of moby (`docker-v29.1.0`), n8n (`n8n@2.4.2`) and LangChain (`langchain==0.3.1`), not their other tags. It adds which matches the watchlist already holds (`already_listed`). More than one match means the person chooses. `agent-runtime/scripts/check_known_projects.py` checks every entry on the list against the real GitHub: that it exists, the address GitHub gives it now, and its newest release under the watch's tag rule. Run it from `agent-runtime/` with `uv run python scripts/check_known_projects.py`, with `GITHUB_TOKEN` set to ask with a token. It exits with 1 when an entry needs a change. CI does not run it, because GitHub's answers change from day to day.

## What the Planner understood

Before a workflow is set up, the Planner reads the Operator's task back in four parts: `schedule` (when it runs), `look_for` (what to look for), `do` (what to do with it) and `where` (where the result goes). Each row is `understood`, `changed` (the Planner read something into the words, and the note says what the task said), `missing` (the task does not say, so `text` is empty) or `cant_do` (no tool does it, and the note says why, even when `text` is empty). There is one schedule row first, then at least one row of each other kind, at most 8 rows.

The rows come from the Planner's answer (`POST /v1/planner/answer`, `planner-answered-card.json` and its neighbours). The old read-back route and the New workflow screen that used it are gone (plan item N22).

Two rules hold whatever the model says. First, every row is held to what the platform can do. That is an allow list, kept as one table in `agent-runtime/src/agent_runtime/abilities.py`: read Jira tickets, sum up what it finds, check software for new releases, and create a Jira ticket after a yes. A row the model marked `understood` or `changed` stays that way only when every action in it is on the list. Otherwise it is `cant_do`, with a note that says in plain words what the platform can't do yet and what it can. A `do` row is a read, a summary or a new Jira ticket, and nothing more: a second action that is not on the list, a write in any form anywhere in the row (close, closes, closing, delete, assign, comment, post, text, restart, open a pull request and the like), or a target outside Jira (a GitHub issue, a Google Sheet, a chat, email) makes it `cant_do`. A `where` row is a Jira project, by key or by name, or a new ticket. A `look_for` row is a search of Jira tickets. It may name other systems as what the tickets are about (tickets about GitLab access, access request tickets for Entra), but a row that reads another system (who has admin access in GitLab) is `cant_do`. A `schedule` row that carries an action ("then delete every closed ticket") is held to the list too. Words count whole and in any form, whatever their case, and quotes and hidden characters do not count. Second, the watchlist word must be in the task and be a form of version, release, upgrade, patch or vulnerability. The answer shows the task's own word: the model's word when the task has it, otherwise the first other form of the same word, so "versioned" never stands in for "version". The software must be a whole word of the task, so "Go" never matches "Google".

When the Planner cannot read a task (no AI model is connected, the model fails, or no answer comes in time), the answer is the offline reply with the fixed starter workflows. A starter carries the `task` it stands for, or `opens: "software_watchlist"`.

## The activity event

Every event has `run_id`, `seq` (gapless from 1 per run), `ts`, `actor {kind, id, display}`, `kind`, `summary` and `data`. `summary` is plain English written by whoever emitted the event, so the Portal never composes English from `data`. `kind` selects the shape of `data`. The schema is a `oneOf` over the kinds, so a TypeScript generator produces a discriminated union.

| Kind | Actor | Data |
|---|---|---|
| `run_created` | user | `use_case_id`, `use_case_version`, `started_by`, `trigger` (`person` or `schedule`) |
| `leg_dispatched` | platform | `leg`, `attempt` |
| `step_started`, `step_retried` | workflow | `step`, `n8n_execution_id`, `try_number` |
| `step_finished` | workflow | `step`, `n8n_execution_id`, `try_number`, `outcome`, `detail` |
| `agent_joined` | agent (the Planner) | `agent {id, display}`, `reason` |
| `agent_step_started` | agent | `step` |
| `agent_step_finished` | agent | `step`, `result` (free-form object) |
| `agent_failed` | agent | `step`, `error_type`, `message`, `retryable` |
| `agent_message` | agent | `speaker {id, display}`, `addressee` (`{kind: "agent", id, display}` or `{kind: "room"}`), `text` |
| `write_action_proposed` | agent | `proposal_id`, `digest`, `actions[] {connector, operation, line}` |
| `approval_requested` | platform | `approval_id`, `steps[] {index, label, status, decided_by, decided_at}`, `link` |
| `approval_announced` | platform | `approval_id`, `channel`, `link` |
| `approval_announce_failed` | platform | `approval_id`, `channel`, `message` |
| `approval_decided` | user | `approval_id`, `step`, `verdict`, `by`, `digest` (the proposal digest the Approver decided on, `null` only on decisions logged before the field was added) |
| `approval_outcome_not_posted` | platform | `approval_id`, `channel` (the name of the channel that had the approval card). The outcome card was not posted, because the channel set up now does not match it |
| `write_action_denied` | safety_checker | `reason`, `detail` |
| `write_action_done` | platform | `connector`, `operation`, `external_reference`, `approved_by[]` |
| `run_succeeded` | platform | `outcome` (`written` or `nothing_to_write`) |
| `run_rejected` | platform | `by`, `step` |
| `run_failed` | platform | `stage`, `reason`, `retryable`, `message` |
| `run_retried` | user | `leg`, `attempt` |
| `support_reported` | user | `request_id`, `reported_by` |

`run_failed.reason` is one of `AgentError`, `WorkflowNodeError`, `TimedOut`, `DispatchFailed`, `WriteFailed`, `SafetyDenied`, `UnboundIntent`, `OutOfOrderStep`. The AI troubleshooter has one rule per reason.

## Sign-in

platform-api has two sign-in modes. `AUTH_MODE` picks one at startup. The contract is the same in both, except that local mode adds `GET /api/v1/dev/users`.

Local mode (`AUTH_MODE=dev`) starts only with a `PUBLIC_BASE_URL` on `localhost` or `127.0.0.1`. Portal routes then read `X-Dev-User`, one of the ids from `GET /api/v1/dev/users`: `alice` (Operator and Approver), `bob` (Approver), `carol` (Operator). Alice starts the fixture runs, so she is refused with `own_work` when she tries to approve them.

Real sign-in (`AUTH_MODE=oidc`) reads an OpenID Connect access token from the `Authorization: Bearer` header and ignores `X-Dev-User`. platform-api checks the token's signature against the identity provider's published keys (RS256 or ES256 only), then its issuer, its audience and its times. The person's id is the `oid` claim, or `sub` when there is no `oid`. Their roles come from the `roles` claim, where `Operator` and `Approver` are the only values that count. [ADR 0018](../docs/adr/0018-sign-in-with-openid-connect.md) explains the choice.

`openapi.json` declares both modes as security schemes: `DevUser`, an API key in the `X-Dev-User` header, and `OidcBearer`, an HTTP bearer token in JWT format. Every route that reads the signed-in user lists both. That means one or the other signs the request in, depending on the mode. A client that reads the contract sees which routes need a signed-in user.

`GET /api/v1/me` answers who the platform takes the caller to be: `id`, `display` and `roles`. The Portal shows that instead of reading the token itself.

Every error the API sends from its own code has the body `{"detail": "..."}`, and each route declares the error statuses it can answer: 401 without a signed-in user, 403 when the user's role does not allow the route, 404 for an unknown id, 409 when the state of the run or approval does not allow the action, and 503 on every signed-in route when the identity provider's keys cannot be fetched, with a `Retry-After` header. In real sign-in a 401 also carries `WWW-Authenticate: Bearer`. The two other error bodies are the refusal on a decision (`RefusalOut`) and the try-again-later answer of the step route (`RetryLater`). Request validation answers 422 in FastAPI's own shape.

## The agent callback

The task request gives the agent `callback {url, token}`. The agent posts each event to `url` with the token in the `X-Callback-Token` header, never in the URL, because query strings end up in access logs. The handler must compare the token in constant time, bind it to the run and task, and give it an expiry.

## Jira's own answers

`fixtures/jira/datacenter/` and `fixtures/jira/cloud/` hold Jira's answers to the calls the one Jira adapter makes (ADR 0035): an issue, a search, a create, the transitions and two errors. They follow Atlassian's REST reference for Data Center v2 and Cloud v3, with made-up values and `example.com` hosts. `platform-api/tests/test_jira_fixtures.py` checks that the adapter reads them and that the practice Jira answers in the same shape. When a sandbox is reachable, replace them with real answers, with every name, address and id changed, and keep the shape.

`platform-api/tests/test_jira_contract.py` runs the adapter against the practice Jira in both flavors in CI. Set `JIRA_CONTRACT_URL`, `JIRA_CONTRACT_FLAVOR`, `JIRA_CONTRACT_TOKEN`, `JIRA_CONTRACT_EMAIL` (Cloud) and `JIRA_CONTRACT_PROJECT`, and the same tests run against that Jira. Each test makes tickets with a fresh marker in their title and labels, so use a sandbox project.

### The Planner on Home

`POST /api/v1/planner/answer` is the Planner's one answer to what an Operator types or taps on Home (`planner/`). The body is `{"text": ...}` (`answer.text.json`) or `{"intent": ...}` (`answer.intent.json`), never both. The builder asks the runtime for a typed request, then adds what only it knows: `similar`, a workflow of the team's with the same name; `already_listed`, the software already on the Software watchlist; and `use_case_id`, the workflow a name in a question means (null when none or several match). The answers are `setup_card`, `part`, `cant`, `watchlist`, `which_software`, `refused`, `abilities`, `ideas`, `check_workflows`, `why_stopped`, `needs_me` and `offline`, one fixture each (`answer.<kind>.json`). An intent never asks the model: `abilities`, `setup_ideas`, `needs_me`, `check_workflows` and `why_stopped` work with no model connected. The state answers carry only an id, and the Portal fills them from its own routes. With no model connected, after 10 seconds, or when the runtime fails or gives an answer it cannot use, the answer is `offline`: why (`no_model`, `too_slow` or `trouble`), a plain message and the three starter workflows (`answer.offline.json`, `answer.offline.too_slow.json`). It is never a guess. Only an Operator is answered (403 for an Approver), and a `why_stopped` for a workflow that does not exist is a 404.

`POST /api/v1/planner/check-part` checks one part the person changed (`check-part.in.json`), by code alone through the runtime's `POST /v1/planner/check-part`: no model. It answers `fits` or `cant_do` with the plain note, what a fix needs and the system (`check-part.fits.json`, `check-part.cant.json`), and 503 when the runtime does not answer.

`GET /api/v1/capabilities` is the runtime's registry with a `state` that code works out, so no screen decides it. A capability that is `planned` or `unsupported` in the registry stays so. A ready one is `needs_setup` when a connection it uses is not set up (its own, or the AI model when it needs one) and `down` when that connection is not answering or needs attention, with the connection's problem as `why` and its `fix`. `agents` lists the agent cards that use its tools. The last good registry is served while the runtime is waking up, and a runtime that never answered is a 503 (`capabilities.json`, and `capabilities.trouble.json` with Jira down and no AI model).
