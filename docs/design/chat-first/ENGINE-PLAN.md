# n8n as the engine behind every workflow: design and build plan

Written 13 Nov 2026 against origin/main `20917504`. It replaces section 6 of `cf/PLAN.md`. Facts about today's code were read from `platform-api/src/platform_api/` and `agent-runtime/src/agent_runtime/` on that commit, the ADRs 0007, 0012, 0020, 0023, 0024, 0026, 0027 and 0034, the P1, P4 and P6 prototypes, the teammate's `n8n-project/`, and n8n 2.42.6's own code in the pinned image. Where a fact still needs proving on a running n8n, the plan says so and sends it to spike P7.

## 0. The engine in one paragraph

Every workflow in the Portal becomes one n8n workflow, built from our node pack (Start from the Portal, Read, Agent, Propose a change, Ask for a yes, Make the approved changes, Tell, Report a failure) and n8n's own Schedule, Manual and Error triggers, IF, Merge, No Op and Sticky Note. n8n runs it, holds the approval wait as a waiting execution, and keeps the execution history that staff see in n8n. Our API stays the only thing that reads, proposes, asks, writes or tells, because our nodes can only call our API, at an address and with a key that come from the container's environment, and the allow list (`NODES_INCLUDE`) leaves n8n no other node that can reach anything. Safety does not depend on the shape of any n8n workflow: the write gateway checks our own records at the moment of each write (ADR 0026). The Portal's screens, words and motion stay exactly as the chat-first sketch shows them; the engine changes only what happens under them.

## 2. The design

### 2.1 Shape

```
Portal ── /api/v1 ──> platform-api ──(public API, owner key)──> n8n
                        │  ▲                                     │
                        │  └──── /internal/v1/n8n/* ◄── our nodes ┘
                        ▼
                 agent-runtime, Jira, GitHub, Confluence, Teams/email flow
```

- n8n starts executions (Schedule Trigger, Start from the Portal, Manual Trigger in the editor, retry). Each execution's nodes call our API in order. Our API runs the agent, stores reads, builds the proposal, sends the Teams request, writes, and records every event. The Portal reads only our API, as today.
- Our API talks to n8n through the owner's API key for the public `/api/v1`. In the pinned 2.42.6 that API already has what the ADRs thought was internal (read from `dist/public-api/v1/openapi.yml` in the image): `GET /workflows/{id}` with `versionId` and `activeVersionId`, `GET /workflows/{id}/history` and `/versions/{versionId}`, `POST /workflows/{id}/publish {versionId?}` and `/unpublish`, `PUT /workflows/{id}/transfer {destinationProjectId}`, `GET /executions/{id}` with `mode`, `retryOf` and `status`, `POST /executions/{id}/retry {loadWorkflow}`, `GET /users`, `/projects`. Three things still need n8n's internal `/rest` with the owner's session, which bootstrap already holds: `GET /rest/workflows/{id}/publication-status` (are the triggers live), `GET /rest/workflow-history/workflow/{id}/publish-timeline` (who published), and `POST /rest/workflows/{id}/run` (a manual run of a draft). Each internal call is one function in `n8n.py` and one line in the P7 evidence, so a version bump has a short checklist.
- Nothing of ours sits in n8n's credential store any more. The nodes read `WAB_API_URL`, `WAB_NODE_KEY` and `WAB_START_SECRET` from the container environment. The `X-Step-Key` credential that bootstrap creates today goes away with the `run` workflow.

### 2.2 The node pack

A TypeScript package `n8n-nodes-wab` in `n8n-node-pack/` at the repo root, built into our own n8n image `deploy/n8n/Dockerfile` (`FROM n8nio/n8n:2.42.6@sha256:526daa…`, copies `dist/` to `/opt/wab/n8n-nodes-wab`, outside the `/home/node/.n8n` volume, and sets `N8N_CUSTOM_EXTENSIONS` to it). The image works offline in DevNet. n8n names every node from a custom extension folder `CUSTOM.<name>`, so the type names are `CUSTOM.wab<Name>`, listed in `n8n-node-pack/node-types.json` for the allow list (E1 found this). The exact call and signing contracts are in `n8n-node-pack/README.md`. Every node:

- has no address field and no credential. `WAB_API_URL` and `WAB_NODE_KEY` come from `process.env` at execute time. P6's "API URL" field is gone;
- sends only fixed fields, always including `execution_id` (`this.getExecutionId()`), `workflow_id` (`this.getWorkflow().id`), `node_name`, `mode` (`this.getMode()`: `manual`, `trigger`, `retry` and the rest as n8n reports them), plus the node's own fixed parameters. n8n does not tell a node which try it is on, so our API counts repeated calls per execution and node;
- treats the API's answer as data. A 4xx with a plain `detail` becomes a `NodeOperationError` with that text, which n8n shows on the node. A 5xx or a timeout throws too. n8n's `retryOnFail` retries every error, a 4xx refusal included, and a node cannot opt out, so a refused call is sent up to three times: our API must answer a repeated refusal the same way (E2 makes refusals idempotent);
- has `retryOnFail`, `maxTries 3`, `waitBetweenTries 2000` set by the Planner on Read, Agent, Propose, Make and Tell, never on Ask for a yes (a wait must not be retried into a second request);
- carries the sketch's inspector sentence in `description` and its subtitle in `subtitle`, so the real editor reads the same as the sketch.

An id that is not in that list is refused at run time too, in every `calls/*` route ("Our API refuses an agent ID it doesn't know", P6).

**Build, version, test.**
- `npm run build` (tsc) and `npm test` (vitest) in `n8n-node-pack/`. Unit tests run each node's `execute` against a fake `this` (n8n's `IExecuteFunctions`) and a fake API, and cover: no call without env; fixed fields only; 4xx becomes a node error with the API's words; 5xx throws; Ask for a yes's four exits; Start from the Portal's 401 on a bad signature, an expired body and a reused nonce; Report a failure's payload shape.
- The package version is the platform's version; the image is tagged with it. `infra/public-images.json` keeps the base pin; CI's `checks` matrix gains `n8n-node-pack`.
- A pack smoke job boots the image with the allow list on, signs in as the owner, reads `/types/nodes.json`, and asserts that exactly the allowed node types load (8 of ours, 3 triggers, 4 flow nodes) and nothing else. It runs on every PR that touches the pack or the pin, and before any move of the pin.
- The e2e stack (`deploy/compose.yaml`) uses this image; `scripts/e2e.sh` is unchanged.

### 2.3 The life of a run

Our API links an execution to a run on the first node call, and the start item decides which run. On that call our API reads `GET /api/v1/executions/{id}` (its `data` holds each node's output, a proven public field) and looks for the Start from the Portal item. n8n saves execution data only at the end unless the workflow has `saveExecutionProgress: true`, so every layout sets it and the checker requires it (2.5); P7 proves the trigger's output is readable mid-run with it on. Fallback if it is not: each of our nodes reads the trigger's item itself with `$('Start from the Portal').first()` and sends it on every call, and our API verifies it exactly as it would from the execution record. A start item names a nonce our API issued for exactly one run (`orchestration.starts(nonce PK, run_id, kind, expires, used_at)`): our API checks the signature itself, refuses an expired or used nonce, marks it used, and links the execution to that run (`orchestration.executions`). So a schedule firing during a Run now, a holder's editor run, or a replayed start can never take a pending run's identity or its `kind`, and a test run is identified by its own nonce even when n8n injected the item through `triggerToStartFrom` and the node's `webhook()` never ran. The link is decided in this order: first `retryOf`, which joins the execution to the original's run (a retry copies the original's start item, so its used nonce is expected and is not refused); then a valid start item, which links by its nonce; then `mode: manual`, which is the holder's run and is refused with "Nobody holds this workflow" when no person holds it, because then only the owner account could have started it; then `mode: trigger`, which is a new run. A `manual` execution that carries a valid start item links by the nonce and still adds the holder as a party. After the link, every later call for that execution is answered against that run. A run holds: `use_case_id`, `n8n_workflow_id`, `n8n_version_id` (the version it ran, read once on the first call), `started_by` (a person or "schedule"), `mode`, the node calls so far with their stored answers, the proposal, the request, the result.

1. **A scheduled run.** n8n's Schedule Trigger fires (Singapore time, `settings.timezone`). The first node (Read or Agent) calls our API. Our API: checks the version it ran (`activeVersionId` from `GET /api/v1/workflows/{id}`, cached 60 s; for a `manual` run the current draft, which it grades on the spot) against the stored versions; if that version failed the safety check, or is unknown, the run stops with "This version failed the check" before it reads anything (ADR 0027). Checks "one waiting run per workflow": an open request for this use case stops the run with `skipped`. Creates the run with `started_by` = the publisher of that version and `mode=trigger`. The publisher comes from our own records: for a version published from the Portal (`published_in: portal`: Turn it on, a schedule change, Undo, roll back, Add the yes back, or a migration), it is the Portal person who acted, never the owner account the timeline names; for a version published in n8n it is the n8n user from the publish timeline, matched by the n8n user id we stored when we created their account (D5). Then does the work of the node, stores the answer under `(execution_id, node_name)`, emits `step_started`/`step_finished`, and returns.
2. **Run now.** The Portal calls `POST /use-cases/{id}/runs` (unchanged route). Our API creates the run `pending` with `started_by` = the person, enqueues outbox `START`, which POSTs the signed body to the trigger's webhook URL (read from the published version's node `webhookId`). n8n answers 200 and starts the execution; the first node call links it. Deadline: `pending` 4 min as today, then `TimedOut`, retryable.
3. **A test run of a draft.** `POST /use-cases/{id}/runs {test:true}` on a draft (PR 8's route). Our API runs the draft by hand: `POST /rest/workflows/{id}/run` with the owner's session, body `{workflowData: <the draft read from /rest>, triggerToStartFrom: {name: "Start from the Portal", data: <the same signed start item>}}` (`workflows.controller.js:327`, P7 proves the body). n8n answers with `executionId` at once. The run is `test`, `started_by` = the person. Every node does real reads. At "Ask for a yes", our API answers `{test: true}`: the node asks nobody, takes no exit, and ends the execution; the run ends `succeeded` with outcome `test_passed`, so the Portal shows `Test run passed up to the yes. Nothing was written.` A Tell in a test run sends nothing: `calls/tell` records `would have posted to {channel} and emailed {n} people` and the build panel shows that line, so a workflow with no yes (the cert reminder) is tested without a real card or email. Nothing was proposed to anyone and nothing written; the gateway would refuse a test run's write anyway (rule in `check()`: `TEST_RUN`). Fallback if P7 fails on the manual run: publish a throwaway copy named `{name} (test)`, run it through Start from the Portal, delete it, as the teammate's `clone-webhook.mjs` does.
4. **The approval wait, held in n8n.** "Ask for a yes" calls `calls/ask` with the resume URL. Our API: if the proposal is empty, answers `nothing_to_change`, the node leaves by that exit and the run ends `succeeded(nothing_to_write)`. Otherwise it creates the approval request (as `_ask_approval` does today: the digest, the named Approvers and the two waits from the use case version), stores the resume URL sealed with the settings `KeyBox`, enqueues `ANNOUNCE` (the same Teams card), and answers `wait`. The node puts the execution to wait. The run is `awaiting_approval`, with a live `waiting` execution in n8n.
5. **Yes.** Bob decides in the Portal (`POST /approvals/{id}/decisions`, unchanged). `decide()` records the decision, enqueues `SHOW_OUTCOME` as today, and enqueues `WAKE {request_id, decision: yes}`. The outbox POSTs the resume URL with that body. n8n resumes; the node's `webhook()` checks the `mac`, reads `decision` and takes the `Yes` exit. "Make the approved changes" calls `calls/write`; the gateway checks our records (2.4) and writes. Until the wake is delivered (n8n answered 200) the run stays `awaiting_approval` and reads "Approved, waking n8n", so an n8n outage does not burn a deadline; it becomes `acting` on delivery, deadline 8 min, then `succeeded(written)`. A 409 on the wake means something else resumed the execution: the run is marked `lost` at once (2.3.13), not after a day.
6. **No.** The same wake with `decision: no`. The `No` exit runs (nothing after it by default; the Planner leaves it open for staff to add a Tell). The run ends `rejected`.
7. **No answer, expiry.** Our in-process tick (`run_forever`, 5 s) keeps ADR 0024's clock: after the first wait it asks the backup and reminds the first Approver; after the second it expires the request. Expiry enqueues `WAKE {decision: no_answer}` and the run ends `expired`, "No answer. Nothing was written." The `No answer` exit runs. n8n's own `waitTill` is year 3000, so n8n never decides.
8. **The write, at the moment it is made.** `check()` keeps its rules and gains two that deny the whole proposal: `EXPIRED` (the request's expiry has passed) and `TEST_RUN`. The subject key is per action, not a deny: the gateway skips an action whose `(use_case_id, subject)` was already carried out in any run and answers "already made in run X" for it, then writes the rest. At ask time, actions whose subject is already done are dropped from the proposal before the Approver sees it, so the list is honest. The write key becomes `(use_case_id, subject)` for actions with a subject and stays `(run, proposal, index)` for the rest. Partial success: "2 of 3 made" is stored per action; a retry carries out only what is not done.
9. **Failure.** A node throws (a read failed after 3 tries, the runtime is down, "2 of 3 made"). The execution ends `error`; the error workflow (2.8) reports it; our API marks the run `failed` with the node's reason and `retryable` as today's `FailureReason` says. If our API already stored the failure from the node's own 5xx path, the report is a repeat and is ignored by `execution_id`.
10. **Retry.** From the Portal (`POST /runs/{id}/retry`, unchanged): after the short delay, our API records `retried_by`, calls `POST /api/v1/executions/{execution_id}/retry {loadWorkflow: false}`, and links the new execution (answer `id`, `mode: retry`) to the same run. n8n resumes at the node that failed, on the version that ran, with the earlier nodes' data. Every node call whose `(run, node_name)` answer is stored is replayed from our store anyway, so even a retry that re-enters an earlier node never runs an agent or adds an action twice. The person who retried joins the parties and cannot approve. In n8n's editor, the holder's own "Retry" makes an execution with `retryOf`; our API reads it from `GET /api/v1/executions/{id}` on the first call and joins it to the same run, with the holder as a party. A retry after the yes keeps the yes: the gateway's keys stop a second write. If P7 finds the public retry wanting (for example it cannot resume a node that threw before calling us), the fallback is a new signed start with `kind: retry, retry_of: run_id`, with the same replay rule.
11. **A run on a version published in n8n that lacks the gate.** The sweep already graded that version `Writes refused` and the Portal shows the banner. The run still starts (staff may have meant it), reads, and reaches "Make the approved changes" with no request: the gateway refuses with "No yes for this run", the node throws, the run fails with `SafetyDenied`, and the troubleshooter names the version and the missing node. Nothing is written.
12. **Tell.** `calls/tell` sends only when all three parts of the Tell rule hold: the recipients are the ones fixed in the Portal's Connections (the node holds a choice, not an address); the content is built by our API from the run's stored reads and agent results, with the `write` results listed only as "made after a yes" when the gateway made them; the registry entry says "Posts in Teams and emails". A Tell never asks for a yes and never claims a change. In a test run it sends nothing (2.3.3). An Agent's `inputs` expressions may feed upstream run data to the model and on to a Tell; that stays within the rule, because the recipients are fixed and the content is the run's own data, and the inputs are size-capped (2.2).
13. **Lost.** If `WAKE` cannot reach n8n (n8n down, execution gone), the outbox retries every 5 min for 24 h, then marks the run `lost`. A 409 on the wake (the execution was resumed by something else, or has finished) marks it `lost` at once. The Operator sees "Approved, but n8n lost the run" with `Make the changes from here`, which calls the gateway directly, as ADR 0026 allows. A workflow deleted while a request waits: see decision D7.

### 2.4 Which of today's run-model pieces change, and how

### 2.5 Building and changing a workflow

**The Planner lays out nodes.** `builder/layout.py` turns a plan into an n8n workflow document. The plan is what the set-up answer already carries (the rows `Watch / When / Then`, the cards and their values, or a template's blocks). The layout is deterministic code, not a model call: the model chooses cards and values (ADR 0023), the code places nodes. Each template or card plan has a layout:

- Release check and the Software watchlist: Schedule Trigger (`When`), Start from the Portal, Read "Read release" (GitHub releases, place = the software), Agent "Compare" (Version checker), IF "Newer?" on `$json.newer`, Ask for a yes, Make the approved changes "Create ticket" (or Tell "Tell you" when `Then` is `Tell me here`), No Op "Nothing to change" on the false branch. The watchlist's Read covers every watched software (place = `the watchlist`).
- Agent cards (one to three): Schedule Trigger, Start from the Portal, one Agent node per card in order, then Ask for a yes and Make the approved changes, with the Nothing to change exit wired to a No Op.
- Every layout gets a Sticky Note with the purpose, the Portal link, and what is safe to change, and `settings = {timezone: "Asia/Singapore", errorWorkflow: <ours>, saveManualExecutions: true, saveExecutionProgress: true, executionOrder: "v1"}`. The checker requires `saveExecutionProgress`, because the run link reads the trigger's output mid-run (2.3).

Node names are the sketch's block labels (`Read release`, `Compare`, `Ask for a yes`, `Create ticket`, `Tell you`, `Nothing to change`), so the run line, the build canvas and n8n all read the same.

**The safety checker grades the draft and adds "Ask for a yes".** Before saving, `workflow_check.grade(document)` runs. When a path reaches a write without a yes, the checker inserts an Ask for a yes in front of it and records the line `Added a yes before the ticket.` in the `build_log`. (The Planner's layouts always include it; the insertion exists for cards and for drafts that people change later.) A draft that grades `Needs a fix` is not saved; the set-up card shows the reason as a crossed row.

**Saving the draft and publishing through the API.** `POST /agent-use-cases {on:false}` (PR 8's route): create the use case `draft`, `POST /api/v1/workflows` with the document (n8n assigns the id; store it), read it back and compare byte for byte (the `set-code.mjs` lesson), store version 0 as "draft in n8n". Answer with `blocks[]` (from the document), the grade, and the `build_log`. `POST /use-cases/{id}/turn-on`: `POST /api/v1/workflows/{id}/activate` (which publishes the current draft), wait for `publication-status` to show every trigger `activated` (up to 20 s; Ask for a yes counts as a trigger there because of its resume webhook, P6 Q1, so the wait expects it), read the version id from `GET /api/v1/workflows/{id}` (`activeVersionId`), store version 1 `published_in: portal` with `published_by` = the person who pressed Turn it on (our record, never the timeline, which names the owner account), state `on`. Every Portal publish records its actor the same way; a version made by Undo, roll back or Add the yes back also records the `authors` of the n8n version it republishes (from `GET /workflows/{id}/history`), and those people join the run's parties beside the actor, so nobody approves a change they wrote. Pause and resume are `deactivate` and `activate`, as today's client already has.

**"Open in n8n": a transfer to the person.** Only for an Operator with n8n access (2.9). `POST /use-cases/{id}/open-in-n8n`: the platform transfers the workflow to the person's own n8n project (`PUT /workflows/{id}/transfer {destinationProjectId}`), records `held_by`, and answers the editor URL (`{N8N_EDITOR_BASE_URL}/workflow/{id}`, from ADR 0034's output). The person edits and publishes in n8n. While held, the platform makes no write to that workflow except the ones the Changed in n8n card offers (Undo, Add the yes back), each under the version compare. `POST …/take-back` (the holder, or any Operator with n8n access, who is then shown as the taker in the versions list) transfers it to the platform's project. The Portal shows `Alice has it open in n8n since 10:02` on the workflow page and in the edit card (section 1, row 10).

**The versions sweep.** Every 60 s, and on demand when an `In n8n` tab opens or the Portal tab regains focus, for each use case with an n8n workflow: `GET /api/v1/workflows/{id}` gives `versionId` (draft) and the active version; the publish timeline gives each publish with its user. A new active version that the Portal has not stored: if the timeline names the owner account, it is the Portal's own publish in flight, so the sweep waits for the Portal's record of that `activeVersionId` and stores nothing itself; otherwise fetch its document, grade it, store it as a new version `published_in: n8n`, `published_by` = the person whose stored n8n user id matches the timeline's user (never by email, D5), and emit a `use_case_version_published` event, which the chat shows as the `Changed in n8n` card (`Safe` / `Writes refused`) and the workflow page as the `Needs a fix` banner. The diff for the card's bullets is a plain comparison of nodes and the Schedule rule (`Now runs every day at 7:30.`, `Deleted "Ask for a yes".`). A `versionId` change with no publish is a draft edit and is shown only as `Draft changed in n8n` on the versions list. A 404 means deleted in n8n (decision D7).

**The version compare before and after every platform write.** `n8n.py`'s `write(workflow_id, expected_version_id, change)`: read the workflow and its `versionId`; refuse if it differs from `expected_version_id` (the one the Portal last stored), apply the change to that document, `PUT`, read back, compare the stored document byte for byte, read `versionId` again and store it. Any mismatch answers `ChangedSince` and the caller shows `Changed again since, in n8n.` with the action offered again. The same wrapper serves Undo, roll back, Add the yes back, schedule changes, and the watchlist's schedule.

**Undo and roll back.** `POST /use-cases/{id}/versions/{v}/undo` and `…/rollback` (PR 12) put version `v` back in use. First choice: `POST /api/v1/workflows/{id}/publish {versionId: <v's n8n version id>}`, which publishes a version n8n still holds in its history and touches no draft, so an open editor tab cannot overwrite it. If n8n no longer holds that version (P7 checks the free edition's history retention), the fallback is `write()` of our stored document under the compare, then publish. Either way the sweep stores the new version `published_in: portal`, `change: rolled back to v`, and the checker grades it; a version that grades `Writes refused` may still be rolled back to (it was published once) but the banner shows at once. Undo on the Changed in n8n card is the same call with `v` = the version before. "Add the yes back" is a `write()` that inserts an Ask for a yes before each write in the current published document, then publishes.

**Change by talking.** `PUT /use-cases/{id}/schedule {day, at, via: 'chat'}` (unchanged route) becomes a platform write: change the Schedule Trigger's `rule` in the published document, `write()` under the compare, `activate`, store the version with `ScheduleChange` as today. `PUT /watchlist/schedule` does the same to the watchlist's workflow, and is refused in the same way while a person holds that workflow (D15). The edit card's words do not change.

### 2.6 Moving the Software watchlist and the existing workflows

Order, with the Azure deploy kept working at each step:

1. **E1 to E3 land with nothing using them.** The image carries the pack; `NODES_INCLUDE` is unset; the `run`, `schedule_tick` and `run_failure_reporter` workflows keep running. The error workflow is rebuilt first to Error Trigger → Report a failure (E3) because Report a failure needs no allow list; the failure route accepts both shapes for the window.
2. **New use cases are born on the new engine** once E4 and E5 land (`engine='own'`). Old ones keep `engine='shared_run'` and keep running through `run` and `schedule_tick`; `Orchestrator` routes by `engine`.
3. **The watchlist moves** (E9): bootstrap, on its next deploy, finds the `software_watchlist` use case, lays out its workflow from the template with its schedule copied from `orchestration.schedules` into the Schedule Trigger, publishes it, stores version N+1 (`Moved to its own n8n workflow`), sets `engine='own'`, and deletes the schedule row. Run history is untouched: runs key off `use_case_id`; `software_checks`, `our_versions` and `proposed_tickets` key off the software and the run. The Watchlist page reads them as before.
4. **Agent use cases move** (E10) the same way, in the same bootstrap step, each with its cards and schedule. A use case with any open run on the old engine (`pending`, `working`, `proposed`, `awaiting_approval` or `acting`) is skipped by that deploy and moved on the next one after the run ends; the bootstrap says so in its log and the Portal shows `Moving to n8n after this run` on its page. A migrated version carries the previous version's publisher as its own.
5. **Retire `run` and `schedule_tick`** (E10): bootstrap deletes them only when no use case has `engine='shared_run'` and no run of the old engine is open. It also deletes the old `X-Step-Key` credential. The old step route goes with the next release.
6. **Turn the allow list on** (E11): `NODES_INCLUDE` set in `deploy/compose.yaml` and Terraform. Bootstrap checks every stored workflow still grades `Safe` or `Writes refused` and that n8n lists exactly the allowed types. If a stored workflow uses a type outside the list (possible only for a workflow made in n8n before E11), the deploy still goes ahead and the Portal shows that workflow as `Needs a fix: uses a block that is now off`.

Every step is one deploy and reverses by redeploying the previous image, with one plain limit: a moved use case has no `schedules` row any more, so under the old image it is dead, not double-running, until the move is redone. The `engine` column and the stored documents stay; the old `run` workflow is recreated by the previous bootstrap. On Azure, the bootstrap job runs before traffic moves, as today, so a failed move stops the deploy rather than the runs.

### 2.7 The cert expiry reminder, rebuilt from our nodes

Layout (template `cert_expiry_reminder`, offered on Home as a chip for the sponsor's team):

```
Schedule "Daily 9:00" ─┐
Start from the Portal ─┴─> Read "Read cert list" (Confluence page: Cert List)
   -> Agent "Find expiring" (Cert list parser)
   -> IF "Anything to report?" ($json.has_alerts)
        true  -> Tell "Tell the team" (Teams channel + email)
        false -> No Op "Nothing to report"
```

- **The Confluence connection.** A new `confluence` connection in `orchestration/connections.py` beside Jira: base URL, email and API token (Atlassian Cloud basic auth, the same kind of token Jira uses), and the list of allowed pages (id and title) that an Operator sets on Settings' Connections tab. `Read` offers only those pages. The read is `GET /wiki/rest/api/content/{id}?expand=body.storage,version`, done by platform-api (`orchestration/confluence_rest.py`), and reaches the runtime as the tool `confluence.read_page` through `GET /internal/v1/runs/{run_id}/confluence/pages/{id}`, the same shape as the Jira reads. Registry: `confluence.read` ready.
- **The parser as a tool.** `agent-runtime/src/agent_runtime/tools/cert_list.py`, a line-for-line port of `parse-build.js` (tables from storage format, the date rules, the buckets, the counts, the card and email bodies, the knobs `WARN_DAYS 60`, `NEAR_DAYS 30`, `STALE_AFTER_DAYS 365`, the row caps). `parse-test.js`'s fixture table and its twelve assertions become `tests/test_cert_list.py`; the counts must match (4 confirmed, 2 without ENV, 1 unreadable, 1 stale, 1 duplicate, 2 not tracked). The fixed agent "Cert list parser" (`cards.py`, a starter card beside `crd_version_checker`) calls the tool, then, when a model is connected, asks the platform's model to interpret `needs_rows` with the teammate's system prompt and the same JSON shape; with no model it emits the "model unavailable" line, which is `merge-ai.js`'s behaviour. Its output item carries `has_alerts`, the counts, `card` and `email_html`.
- **Tell to Teams and email.** One Power Automate flow, "Tell", with the trigger "When an HTTP request is received", the action "Post adaptive card in a chat or channel" and "Send an email (V2)", as the teammate built. Its URL (the `sig` is the secret) lives in Key Vault as `teams-tell-webhook-url` and reaches platform-api as `TEAMS_TELL_WEBHOOK_URL` through `make-env.sh` and Terraform like `teams-webhook-url` today. `orchestration/tell.py` posts `{card, emailSubject, emailHtml}`; in the e2e stack the Teams stub records it. The email recipients are the Connections tab's fixed list, never a value from the page. Registry: `teams.post` and `email.send` become ready as one entry, "Posts in Teams and emails".
- **The platform's model in place of Ollama.** The agent uses `ModelAccess` like every card run. No reachability probe is needed; "no model connected" is a known state.
- **Secrets.** Key Vault: `confluence-api-token`, `teams-tell-webhook-url`. Settings, not secrets: the Confluence base URL and email, the page list, the email list, the Teams channel name. n8n's credential store: nothing. The repo: nothing; `n8n-project/` moves to `docs/evidence/n8n/cert-reminder/` unchanged, as the record and the fixture source.

### 2.8 The error workflow under the allow list

`run_failure_reporter.n8n.json` becomes Error Trigger → Report a failure. Report a failure reads the trigger's item and posts it to `/internal/v1/n8n/failures`. Our API maps `execution.id` to the run; if no node had called yet it creates a `failed` run for the workflow's use case so the Portal shows it (`Stopped before it read anything`). Because the Error Trigger's payload has no run id, the link table is what makes the mapping (ADR 0007's complaint, answered).

Bootstrap loads it first and sets its id into every workflow it creates; the checker flags a workflow whose `settings.errorWorkflow` differs.

**A held workflow.** n8n runs an error workflow only when the failing workflow's project can reach it, and a workflow transferred to Alice's project sits apart from the platform's error workflow, which the free edition cannot share. P7 tests a failing workflow in a member's project. If the error workflow does not fire there, the fallback is built in from E2c: the sweep lists `GET /api/v1/executions?status=error&workflowId=…` for every linked execution that our API has not already closed, reads the failed execution's `data` for the node and its error text, and fails the run with those words, so nothing is lost but a minute. The daily self-test then also runs a copy in a member's project, so the fallback is proven every day too. The daily proof (ADR 0027): `self_test_failure.n8n.json` is Start from the Portal → Read with place `self-test`, which our API answers with an error on purpose. The in-process tick starts it once a day at 06:00 and expects a failure report within two minutes, else `/healthz/ready` reports "the error workflow did not report" and the Operator sees it on Settings. The old daily check (is it active?) stays as the fast check.

### 2.9 n8n access and "Open in n8n" on the free edition

- **The flag.** `people.n8n_access boolean`, set by an Operator on Settings' People tab, only on Operators; `me.n8n_access` in the contract; the Planner's reply for everyone else is the sketch's `Only people with n8n access can open n8n. An admin can add it in Settings.` Approvers can never hold it: giving someone the Approver role drops the flag, with a line on the People tab saying so.
- **The n8n account.** When the flag turns on, the platform creates the n8n member with the same email through n8n's invitations (P6 showed inviting a member works on the free edition; P7 checks the public `POST /users`, which the openapi grep did not show, else `/rest/invitations`), stores the n8n user id on the person, and shows the person, on their own Settings page, a one-time `Set your n8n password` link built from the invite. Every later match of an n8n user to a person is by that stored id, never by email, which a member can change in their n8n profile. One editor sees only what sits in their own project, so they see only workflows transferred to them.
- **Not before the allow list.** Account creation and "Open in n8n" stay behind the setting `N8N_STAFF_ACCESS`, which E11 turns on with `NODES_INCLUDE`. Until then the flag can be set, but the Planner answers `Opening n8n is coming once the block list is on.` With the editor on the internet (ADR 0034), a member with a held workflow and no allow list could add an HTTP Request node and send what a run read anywhere, which is the leak ADR 0027 closes; the chain E3, E10, E11 is what has to land first.
- **One editor at a time.** A workflow sits in one project. "Open in n8n" transfers it; the Portal shows who holds it; "Take back" returns it. Whoever holds it can publish. Every publish is a version in the Portal, with the publisher's name from the timeline (2.5).
- **What the editor can do.** With the allow list, the palette has our eight nodes, three triggers, IF, Merge, No Op and Sticky Note. Credentials the person adds are unusable by any node. The owner account (the platform's) is managed by the environment (ADR 0034), so staff cannot change it.
- **Editor address.** ADR 0034's `N8N_EDITOR_EXTERNAL` switch and allow list stay; "Open in n8n editor" links to `n8n_editor_url`. In DevNet the address is internal.

### 2.11 How this meets PR 8 and PR 9

### 4.2 What could go wrong, and the guard

| Threat | Guard |
|---|---|
| A maintainer deletes or moves Ask for a yes in n8n and publishes. | The gateway refuses with "No yes for this run"; the sweep grades the version `Writes refused` and the chat gets the card with `Add the yes back`. The run page's troubleshooter names the version. Nothing is written. |
| A stale editor tab autosaves an old draft over a platform write. | Every platform write compares `versionId` before and after and reads back byte for byte; a loss shows `Changed again since, in n8n.` Undo and roll back prefer `publish {versionId}`, which no autosave can overwrite. Schedule edits are refused while someone holds the workflow. |
| A replayed or guessed resume URL. | n8n signs the URL (P1 Q3: 401 without the signature) and answers 409 on reuse (P6 E). A wake without our `mac` gets 401 from the node and leaves the execution waiting, so a foreign wake cannot consume the wait and strand the real yes. Whether a refused resume leaves the execution waiting is a P7 question; if n8n ends the execution anyway, the fallback is already in place: `WAKE` meets a 409 and the run is marked `lost` at once, and the Operator finishes from the Portal. The gateway reads only our records, so even a successful foreign wake writes nothing. If `WAKE` meets a 409 anyway, the run is `lost` at once and the Operator can finish from the Portal. The URL is stored sealed. |
| A replayed start, or a start that lands on the wrong run. | Our API links an execution by the nonce in its start item, issued for one run and marked used on first sight; a second execution with the same nonce is refused and ends with "This start was already used". A pending run can never be claimed by a schedule firing, a holder's run or another start. |
| A forged start to Start from the Portal. | HMAC with a secret only our two containers hold, 5 min expiry, nonce, and the run must exist and be `pending`. Without a valid body the node answers 401 and starts no execution. Noise cannot create runs. |
| Two runs of one workflow at once (Run now during a wait, a schedule moved earlier, a manual run). | "One waiting run per workflow" at the first call: the later run ends `skipped` with the sketch's words. Approvers never see two requests for the same change. The subject key stops the same ticket twice across runs. |
| n8n down in the middle of a wait. | The waiting execution is rows in n8n's Postgres; it is still waiting when n8n returns. `WAKE` retries for 24 h; then the run is `lost` and the Operator can make the approved changes from the Portal, because the gateway needs no n8n. |
| n8n's database lost. | Our records hold the run, the proposal, the request and every version's document. Runs in flight become `lost`; approved proposals can still be carried out from the Portal; workflows are recreated from the stored documents by bootstrap (`Restore to n8n`). |
| The node key leaks. | It is an environment value, not a credential, so no one in the editor can read it. With it, a caller can make node calls; every write still needs a yes recorded by a signed-in Approver, and reads are limited to the allowed places. Rotation is one Key Vault secret and a restart. |
| Staff add their own Jira or HTTP keys in n8n. | No node on the allow list can use a credential. P6 Q6 and Q5 together; `test_allow_list` keeps it true. |
| A workflow made in n8n reads Jira or Confluence and Tells it to a channel. | Read reaches only the allowed places; Tell reaches only the fixed channel and list; the content is composed by our API. Nothing can be sent elsewhere. |
| A retry after a write, or an execution retried in n8n. | The write key and the subject key stop a second write; node answers are replayed. |
| Make the approved changes placed twice, or before Ask for a yes. | The second call finds every action done and answers "already made"; the first-before-yes call finds no request and is refused. |
| The publisher's n8n email matches nobody in our People list. | Runs of that version stop at the first call (D5) rather than start with nobody as a party. |
| An n8n upgrade changes `/rest` or the node API. | The pin is by digest; the pack smoke and the P7 checklist run before the pin moves; the three `/rest` uses are isolated in `n8n.py`. |
| The pack's `loadOptions` leaks data to the editor. | Options are names and ids from the Portal's settings; never run data. |
| The editor is on the internet (ADR 0034) and someone signs in. | They see only their own project, can add nothing that reaches out, and every publish is graded and named. ADR 0034's allow list recommendation stands. |

## 5. The ADR changes

Both ADRs move to `status: accepted`, dated 13 Nov 2026, with the text below appended under a heading `## Accepted on 13 Nov 2026, with these additions`. Earlier ADRs that this supersedes get `status: superseded by ADR 00xx` in their front matter.

### 5.1 Text to add to ADR 0026

> **Accepted on 13 Nov 2026, with these additions.**
>
> **A notice needs no yes (the Tell rule).** A Teams card or an email that only reports what a run read may go out without an Approver, when all three hold: its recipients are fixed in the Portal's Connections, not chosen per run from the data; its content is composed by our API from the run's stored reads and agent results, never from text in a node; and the Portal says what it does, "Posts in Teams and emails". A change to data in Jira or Confluence always needs a yes. A Tell never claims a change was made unless the write gateway made it.
>
> This rule replaces the consequence above that read "Posting in Teams is a write, so it goes through the gateway too": a Tell is a notice under this rule, and a Teams message that asks a question or carries a change stays a write.
>
> **The write gateway gains two checks** that deny a proposal: the request has not expired, and the run is not a test run. A third rule is per action: an action whose subject key was already carried out for this use case in any run is skipped as "already made", and dropped from the proposal before the Approvers see it. The write key is `(use case, subject)` where the action has a subject, else `(run, proposal, index)`. A part-done proposal is recorded per action, so a retry carries out only what is not done.
>
> **How a run is linked.** Our API links an n8n execution to a run on the first node call by the start item it finds in the execution's data: a nonce our API issued for exactly one run, checked and marked used by our API itself, never by the node alone. An execution started by a trigger with no start item is a new run; one started by hand in n8n is the holder's run, and is refused when nobody holds the workflow.
>
> **Whose work, from our records.** For a version published from the Portal, the publisher is the Portal person who acted, from our records; n8n's timeline names the owner account there, which is nobody. For a version published in n8n, the publisher is the n8n user, matched by the user id stored when the platform made their account. The authors of a republished version are parties too.
>
> **Retries.** A retry from the Portal uses n8n's own retry of the failed execution, after the short delay, and our API records who retried. Our API answers a repeated call for the same run and node with its first answer, so no retry runs an agent twice or adds an action twice.
>
> **A lost wake.** If our API cannot wake a waiting execution for a day, the run is lost and the Operator may carry out the approved proposal from the Portal. A workflow deleted while a request waits ends the request as cancelled, with nothing written, and tells the Approvers.
>
> **Test runs** run the draft by hand in n8n, read for real, and stop at "Ask for a yes" without asking anyone; the gateway refuses any write from a test run.
>
> **Whose work, made fail-safe.** A version published in n8n whose publisher is not matched to a person on our People list cannot run until an Operator matches the person.
>
> **Two lines marked "P7 confirms"**: the manual run of a draft and n8n's public retry are the chosen mechanisms; the spike P7 confirms both on 2.42.6 before the code that relies on them lands, and each has a named fallback.
>
> This ADR supersedes ADR 0007. ADR 0024 is accepted at the same time, unchanged, because this engine builds its two waits and its expiry. The glossary's "Leg" is retired. `AGENTS.md`'s safety rules gain: "n8n holds no write key, and the write gateway checks every approval itself at the moment of writing", and "a notice that only reports what was read may go out without a yes, under the Tell rule".

### 5.2 Text to add to ADR 0027

> **Accepted on 13 Nov 2026, with these additions.**
>
> **Every workflow is its own n8n workflow, built by the Planner from our node pack,** including the Software watchlist. The platform's one generic `run` workflow and `schedule_tick` retire once every use case has moved. The node pack is: Start from the Portal, Read, Agent, Propose a change, Ask for a yes, Make the approved changes, Tell, Report a failure. The allow list is exactly: those eight, n8n's Schedule, Manual and Error triggers, IF, Merge, No Op and Sticky Note. n8n's data nodes join only after P7 shows that none can send data out or run code.
>
> **The version compare.** An open n8n editor tab can autosave an old draft over a change made through the API (the team saw it twice in November). So the platform compares the workflow's `versionId` before and after every write it makes to n8n, reads the stored copy back, and reports "Changed again since, in n8n" when it lost. Undo and roll back prefer n8n's publish of an earlier version id, which no autosave touches. The platform makes no other write to a workflow while a person holds it in n8n.
>
> **Our API's address and key come from n8n's container environment,** never from a node field or a credential. Start from the Portal checks a signed body with a secret from the same environment, with an expiry and a nonce.
>
> **On the free edition:** the platform transfers a workflow to the person who opens it in n8n, shows who holds it, and takes it back on request; whoever holds it can publish; the platform creates each person's n8n account with the same email when an Operator gives them n8n access, and stores the n8n user id for every later match; Approvers never get n8n access, and gaining the Approver role drops it. No staff account exists before the node allow list is on.
>
> **The safety checker's grade** covers the allow list, a yes before every write, the trigger, the error workflow, Singapore time, the fixed Tell choices, and a schedule interval longer than the expiry wait, so a request always expires before the next scheduled run. The grade is not the barrier; the gateway and the allow list are.
>
> **The Portal reads n8n's public API for versions and executions, and three internal endpoints** (publication status, the publish timeline, and a manual run of a draft), each kept in one function and re-proven before the pinned n8n version moves.
>
> **Report a failure** replaces the HTTP node in the error workflow, and a daily self-test workflow fails on purpose to prove the chain.
>
> **The Software watchlist and the existing use cases move** by a bootstrap step that lays out each one from its template with its schedule copied into the Schedule Trigger; run history keeps its use case id, and a use case with a request still waiting moves on the next deploy.
>
> **The cert list expiry reminder** is the first non-Jira workflow, rebuilt from our nodes: Read Confluence, an agent with the parser as a tool, and Tell to Teams and email; its original stays in `docs/evidence/n8n/cert-reminder/` as the record.
>
> This ADR supersedes ADR 0012 and ADR 0020. It amends ADR 0023's "one generic n8n workflow carries every card's runs" (each use case now has its own) and ADR 0034's list of what dropping the address allow list would take (the webhooks are replaced and the Webhook node is off the list; sign-in in front of n8n remains). ADR 0024 stands unchanged: our API keeps the clock.

## 8. Changes after the safety review

The review is in `review.md` beside this plan. Every must-fix and should-fix is in; the nits are in too.

- **M1 (Portal publishes named the owner account).** The publisher of a `published_in: portal` version is the Portal person who acted, from our records; a migrated version carries the previous publisher; the fail-safe stop applies to n8n publishes only. 2.3.1, 2.5, 2.6, D5, 5.1.
- **M2 (how the first call finds its run).** The start item is a nonce our API issued for one run; on the first call our API reads the execution's data, verifies the item itself, marks the nonce used and links by it. Trigger runs with no item are new runs; manual runs are the holder's, refused when nobody holds the workflow; retries join by `retryOf`. Test runs through `triggerToStartFrom` are covered the same way. 2.2 (the trigger row), 2.3 opening, 2.3.3, D4, D6, 4.2, 5.1, P7.
- **M3 (a test run with a Tell).** `calls/tell` sends nothing in a test run and records "would have posted to {channel} and emailed {n} people"; the build panel shows it. 2.2, 2.3.3, 2.3.12, D19, test `test_test_run_tell_sends_nothing`.
- **M4 (error workflow for a held workflow).** P7 tests it; the fallback (the sweep lists error executions for linked runs and fails them with the node's words) is built in E2c, and the daily self-test also runs a copy in a member's project. 2.8, E2c, P7, test `test_failure_in_held_workflow_is_reported`.
- **M5 (staff accounts before the allow list).** Account creation and Open in n8n sit behind `N8N_STAFF_ACCESS`, which E11 turns on; E7 now lands after E11; the chain E3, E10, E11 is named. 2.9, E7, the order.
- **M6 ("Test run passed on practice Jira").** Section 1 row 3 now uses PR 8's words, `Test run passed up to the yes. Nothing was written.`, with the write block's tag visible and `on practice Jira` only when a write happened after a yes; it notes the sketch line needs the same edit.
- **S1.** The subject key is a per-action skip, not a deny of the whole proposal; done subjects are dropped at ask time. 2.3.8, 5.1, E2d.
- **S2.** The wake carries a `mac` over `{execution_id, request_id, decision}` with `WAB_NODE_KEY`; the node answers 401 and picks no exit; a 409 on `WAKE` marks the run lost at once; P7 checks that a refused resume stays waiting. 2.2, 2.3.5, 2.3.13, 4.2.
- **S3.** `acting` and its deadline start when n8n accepts the wake; until then the run reads "Approved, waking n8n". 2.3.5, 2.4.
- **S4.** The `authors` of a republished version join the parties; n8n users are matched by the stored user id, not email; a manual run on a workflow nobody holds is refused. 2.3.1, 2.5, 2.9, D5.
- **S5.** The migration skips any open run, not only `awaiting_approval`; the rollback limit (a moved use case is dead under the old image, never double-running) is stated. 2.6.
- **S6.** ADR 0026's "Posting in Teams is a write" is struck in favour of the Tell rule; the publisher rule and the start-item check are in the ADR text; the checker gains "the schedule interval is longer than the expiry wait"; E0 accepts ADR 0024 unchanged. 2.4, 5.1, 5.2, E0.
