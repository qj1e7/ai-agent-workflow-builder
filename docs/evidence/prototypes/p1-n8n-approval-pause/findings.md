# n8n approval pause prototype (THROWAWAY)

Path: docs/evidence/prototypes/p1-n8n-approval-pause

Version: n8n 2.42.6 (same as the October sandbox), Node v26.11.1 (n8n declares engines node>=24), SQLite default DB, one local process, no Docker. Single runs, local machine. Every result below was observed, not inferred.

## Setup that worked
- `npm i n8n@2.42.6 --no-audit --no-fund` in DIR (about 7 min, no sandbox problem; npm skipped install scripts and n8n still started).
- `. ./env.sh` (N8N_USER_FOLDER=DIR/n8n-data, N8N_PORT=5688, telemetry off) then `./node_modules/.bin/n8n start`.
- Owner created via `POST /rest/owner/setup`, API key via `POST /rest/api-keys` (scopes: workflow read/list/create/update/activate/deactivate, execution read/list; `workflow:execute` is not a valid scope).
- Workflows loaded and activated through the public REST API (`load.py`): `POST /api/v1/workflows`, then `POST /api/v1/workflows/{id}/activate`. Both worked, JSON files `wf_*.json` generated by `gen.py`.
- Stub: `python3 -I stub.py` on 127.0.0.1:5690 (event sink, agent, mock Jira, approval stub).

What did NOT work: `n8n import:workflow --input=f.json --activeState=fromJson` fails with "The --activeState=fromJson flag can only be used when n8n is running in queue or multi-main mode. In regular deployment mode, workflow activation is not supported." The CLI import therefore cannot activate in our deployment shape (the first import call also errored, I did not dig into why). Use the REST API to create and activate. The public API POST rejects `id` and `active` fields, so it assigns its own workflow ids.

## Q1 Start: VERIFIED
Webhook node (responseMode=responseNode) followed by a Respond to Webhook node. Our API sends its own request_id in the body.
```
$ curl -i -XPOST localhost:5688/webhook/release-check -d '{"request_id":"req-A1"}'
HTTP/1.1 202 Accepted
{"accepted":true,"request_id":"req-A1"}      total=0.037s
```
The run kept going after the reply: stub log shows run_started, agent call, agent_done, approval register, awaiting_approval within about 85 ms of the request.

## Q2 Pause: VERIFIED
Wait node (resume=webhook, POST). A workflow node passes `{{ $execution.resumeUrl }}` to the stub, keyed by `apr-<request_id>`:
```
APPROVAL REGISTER {"approval_id":"apr-req-A1","request_id":"req-A1","resume_url":"http://localhost:5688/webhook-waiting/1?signature=<redacted-4>"}
```
The URL contains n8n's execution id (`/webhook-waiting/1`) plus an HMAC-style `signature` query value. The stub then resumed it with `POST /approvals/apr-req-A1/decide {"decision":"approved","approver":"alice"}`:
```
RESUME -> .../webhook-waiting/1?signature=...    RESUME RESULT 200 {"message":"Workflow was started"}
JIRA WRITE {"request_id":"req-A1","approver":"alice",...}
```
The decision and approver arrive in the Wait node output as `$json.body.decision` and `$json.body.approver`. n8n does no check on them. Anyone holding the URL can send any approver name.

## Q3 Double and late resume: VERIFIED
- Second resume after finish: HTTP 409, `The execution "1 has finished already.`
- Concurrent resume (3 parallel calls to one waiting run): one got 200, two got HTTP 500 `There was a problem executing the workflow`; n8n log: `Execution is already being resumed by another process (execution 3)`. Exactly one mock Jira write.
- Guessing the id without the signature: `POST /webhook-waiting/2` gives 401 `{"error":"Invalid token"}`. A wrong signature (`?signature=deadbeef`) gives the same 401. Using the normal webhook path with the id (`/webhook/2`) gives 404. Mock Jira writes stayed empty. So the URL is signed and the execution id alone is not enough. I did not test whether the signature can be forged without n8n's encryption key; it is only observed to reject my two guesses.
- Unknown: how long a waiting run survives, and whether it survives an n8n restart (not tested).

## Q4 Reject: VERIFIED
Run req-B1 resumed with `{"decision":"rejected","approver":"bob"}`. The IF node took the false branch. Mock Jira write log after the reject: `[]`. Events: run_started, agent_done, awaiting_approval, run_finished_rejected (approver bob).

## Q5 Events: VERIFIED
Each step is an HTTP node that POSTs `{request_id, step, n8n_exec}` to the sink. Stub log, approved run req-A1:
```
18:19:59.635 run_started
18:19:59.653 agent_done
18:19:59.666 awaiting_approval
18:20:09.307 run_finished_approved   (Jira write at 18:20:09.301)
```
Rejected run req-B1:
```
18:20:18.784 run_started
18:20:18.787 agent_done
18:20:18.790 awaiting_approval
18:20:21.008 run_finished_rejected approver=bob
```
Note: the "paused" signal has to be an event sent before the Wait node. n8n does not tell us when the Wait actually started. Events arrive in order here, but ordering is only by our own timestamps, not guaranteed by n8n.

## Q6 Errors: VERIFIED
Run with a node that calls `http://127.0.0.1:1/dead`, workflow setting `errorWorkflow` pointing at the error workflow.
- Error workflow ACTIVE: it fired. Event: `{"step":"error_recovered_request_id","request_id":"req-E1","failed_exec":"4","failed_node":"Dead HTTP call","message":"The service refused the connection - perhaps it is offline"}`.
- The error trigger payload has only `execution.{id,url,error,lastNodeExecuted,mode}` and `workflow.{id,name}`. It does NOT contain our request_id (checked: "req-E1" not in the payload). I recovered it by calling `GET /api/v1/executions/4?includeData=true` with an API key and reading `data.resultData.runData.Webhook[0].data.main[0][0].json.body.request_id`. A cheaper route that I did not build: have the stub remember exec id to request_id from the run_started event, which already carries `n8n_exec`.
- Error workflow INACTIVE (deactivated by API): run req-E2 failed, no error event arrived, n8n log: `Calling Error Workflow for "J19l8qQqgjIWJR2K". Workflow "ERHsHU82eXbevlkb" is not active and cannot be executed`. Confirms the October lesson. It is a silent skip, only visible in the n8n log.

## Q7 Timing (ROUGH, single run, local machine)
- Start to paused: webhook reply 37 ms; request to awaiting_approval event about 85 ms.
- Resume to finished: resume call 18:20:09.252, finished event 18:20:09.307, about 55 ms (resume returned in about 22 ms; the remaining steps ran after the reply).
Mock services, no real network. Real agent, Teams and Jira latency will dominate.

## Design implications
- Our API must be the owner of approval state. The stub keeps `approval_id (ours) -> resume_url`; the n8n execution id appears only inside that opaque URL and is never used as our token. This works as designed.
- The resume URL is a bearer secret. Store it server side only, never send it to the browser or to Teams card text. Our approval endpoint should be the only caller.
- n8n does not check who approves. The self-approval rule and the two-approver ordering must be enforced in our API before it calls the resume URL. n8n will accept any approver string.
- Safety needs a second layer. The write node must sit after the Wait and an IF on our decision, but anyone who can edit the workflow can remove that. The safety checker must live in the Agent API / mock connector side (deny write unless it can see an approved request_id), not only in the n8n graph.
- Idempotency: n8n already gives one winner on parallel resumes (the losers get 409 or 500), but the 500 is noisy. Our API should record the decision first (one row per approval id, first write wins) and call resume at most once, treating 409 as already done.
- Events: n8n has no built-in event push to us. Each step needs an explicit HTTP node, which is verbose in a generated workflow. The builder should generate these event nodes, including one before every Wait.
- Error handling: the error workflow gets the n8n execution id but not our request_id. Plan for the stub-side mapping (exec id to request_id) or an API-key call. Also add a check that every generated workflow has an active error workflow, since n8n skips an inactive one silently.
- Deploy: loading and activating workflows has to use the REST API, not `import:workflow --activeState`, in single-instance mode.
