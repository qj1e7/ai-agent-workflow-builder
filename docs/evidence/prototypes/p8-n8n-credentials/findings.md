# n8n 2.42.6 Community edition: keys, the member's editor and the credential sweep (spike P8)

Path: docs/evidence/prototypes/p8-n8n-credentials/findings.md

This answers the credential questions ENGINE-PLAN E17 gives spike P8, and the ones that building
E16 and E17 raised (ADR 0045, as amended on 15 Nov 2026). The proxy questions moved to E18 and
are not here.

**How each answer was found.**
- READ means it was read in n8n 2.42.6's own compiled code, copied out of the pinned image
  `n8nio/n8n:2.42.6` with `docker create` and `docker cp` (no container ran). The file is named
  from `/usr/local/lib/node_modules/n8n/dist/`.
- OBSERVED means the e2e suite saw it on the real stack in CI. `e2e/tests/test_n8n_keys.py`
  prints one `P8 OBSERVED` line for each, and the CI run's log holds them.

| # | Question | Answer | How it was found |
|---|---|---|---|
| Q1 | Do n8n's credential type and node type policies (`type-availability-policies`) work on the free edition? If they did, they would replace the sweep. | No. Every route is `@Licensed(TYPE_AVAILABILITY_POLICIES)`, and the check itself allows everything when that licence is missing. The sweep stays. | READ: `modules/type-availability-policies/credential-type-policy.check.js` line 80 (`if (!isLicensed(...)) return NO_VIOLATIONS`), the module's `licenseFlag`, and `public-api/v1/controllers/credential-type-policies.public.controller.js`. OBSERVED: `test_type_availability_policies_are_licensed_only` reads both instance policies as the owner and n8n refuses them. |
| Q2 | What does a member's editor offer from the platform's project? | Nothing. A member lists only the keys their own space holds, and reading one of the platform's keys by id is refused. Sharing a key with another project, which would offer it, is licensed. | OBSERVED: `test_member_cannot_select_platform_credential` lists a member's keys and reads each platform key by id. READ: `credentials/credentials.service.js` (`getManyAndCount` returns every key only to a user with the global `credential:list` scope, the owner). |
| Q3 | How do keys move with a workflow? | They do not. Moving a workflow to another project moves no key, and the platform never moves its own (ADR 0045 as amended). The public API can move a key (`PUT /credentials/{id}/transfer`, scope `credential:move`), and the platform's API key no longer holds that scope. | READ: `public-api/v1/openapi.yml`, `/workflows/{id}/transfer` and `/credentials/{id}/transfer`. OBSERVED: `test_member_hand_run_with_own_key_is_swept` prints where the platform's keys sit while a member holds a workflow: still in the platform's project. |
| Q4 | Does n8n keep a reference to a key when a member who cannot use it saves the workflow, or drop it? | It keeps it. On Community, saving resolves each reference by its id and type wherever the key sits, with no access check. The check that would stop it, `preventTampering`, and the one on create, run only when sharing is licensed. So the put-back on every take-back usually changes nothing, and still covers a reference a member changed or dropped. | READ: `workflow-helpers.js` `replaceInvalidCredentials` (lines 185 to 272), `workflows/workflow.service.js` line 335 (`if (isSharingLicensed()) preventTampering`), `workflows/workflow-creation.service.js` line 194. OBSERVED: `test_builtin_read_and_notice` saves a workflow naming `wab-slack-send` as a member and reads the reference back. |
| Q5 | Can a member's workflow run with a key outside the member's own space? | No. Before a run, n8n refuses a key the workflow's project cannot use, unless the project is the personal project of a user with the global `credential:use` scope, which is the owner. So a held workflow cannot run with a platform key, and a workflow in the owner's project can run with any key there is. | READ: `executions/pre-execution-checks/credentials-permission-checker.js` `findInaccessible` (the owner bypass), and `isCredSharingEnabled`. |
| Q6 | Can a member edit a key in their own space? | Yes, and only an n8n-managed key cannot be. So a key lent to a member could be pointed at their own server, and its secret read. n8n's credential overwrites (`CREDENTIALS_OVERWRITE_DATA`) do not stop it: they fill only empty fields. This is why no key is lent. | READ: `credentials/credentials.controller.js` `updateCredentials` (the only guard is `isManaged`), `credentials-overwrites.js` `applyOverwrite`. |
| Q7 | Does n8n's own connection test check what a key may do? | No. It only checks that the key works: Jira's asks `/rest/api/2/myself`, GitHub's `/user`, Slack's `users.profile.get`. So the platform asks each system what the key may do itself, against a list of what reading or posting needs. | READ: `n8n-nodes-base/dist/types/credentials.json`, the `test` of `jiraSoftwareServerPatApi`, `jiraSoftwareCloudApi`, `githubApi` and `slackApi`. |
| Q8 | Does pinned output stop a block running in a test run, and only there? | Yes. n8n uses a workflow's pinned output only when a run is by hand (`manual`) or an evaluation, which is what a test run is, and ignores it in every other run. | READ: `workflow-runner.js` `resolvePinData` and `webhooks/webhook-helpers.js` line 437. OBSERVED: `test_builtin_read_and_notice` prints the posts the mock Slack saw after a test run (none) and after a real run (one). |
| Q9 | What does n8n add to a node with a key that the static node list does not show? | Two things. A "Custom API Call" choice in every resource and operation list of Jira, GitHub, Microsoft Teams 2 and Microsoft Outlook 2, which sends any request with the node's key, and a human-in-the-loop AI tool of Slack, Teams, Outlook and Gmail. The class file turns all of them off, and the pin check names each. | OBSERVED: the pin check in `scripts/pack-smoke.sh` on the pinned image, CI run 43722956710 (43 Custom API Call choices and 4 tools named before the class file was put right). |
| Q10 | Can Teams, Outlook or Gmail use a key the platform can hold and check? | No. n8n's Teams block posts to a channel only with a person's own sign-in ("app-only Graph supports only migration import"). Its Gmail block asks Google for `gmail.modify` and `mail.google.com`, so a send-only key fails. n8n rewrites an Outlook app key each time it gets a token (`preAuthentication` persists `accessToken`), so the sweep could not tell a change from a refresh. | READ: `nodes/Microsoft/Teams/v2/actions/channelMessage/index.js` line 110, `nodes/Google/GenericFunctions.js` lines 61 to 68, `credentials/MicrosoftEntraServicePrincipalApi.credentials.js` lines 116 to 228, and `credentials-helper.js` line 127. |
| Q11 | Can a key be shared with a project use-only, so a member could use it without seeing or editing it? | Not on Community. Sharing a key with another project is licensed (`isSharingLicensed`), and a shared key is still the owner's to edit. It could be a later option with a licence; nothing is built on it. | READ: `credentials/credentials.controller.js` and `public-api/v1/controllers/credentials.public.controller.js` (`isGlobal` and sharing both need `isSharingLicensed`). |

**What stays open.** Nothing here is a guess. The OBSERVED rows rest on the e2e run named in the
PR, whose log prints each `P8 OBSERVED` line.
