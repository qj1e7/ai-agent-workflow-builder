# The Planner on the real model: baseline, 15 November 2026

The team lead tested the app with the real model and got poor answers to ordinary sentences. Their goal: "user should be able to type anything they want and expect a proper and logical and meaning, useful response back." This page measures how far main is from that goal, before any fix. Nothing in the Planner changed for it.

The full report, with every failure, the sentence, the answer kind and the words shown, is in [2026-11-15-baseline-report.md](2026-11-15-baseline-report.md). The answers of the `anything` job, with the model's own reading of each, are in [2026-11-15-baseline.json](2026-11-15-baseline.json).

## What was measured

- **Models.** Claude Haiku 4.5 (`claude-haiku-4-5-20251001`), the app's model, and Claude Sonnet 5.5 (`claude-sonnet-5-5`), the strongest model the AI Singapore gateway lists. It lists no Opus.
- **Cases.** Every golden set in `agent-runtime/evals/cases/`, and the new `anything` set: 123 sentences in 14 categories, with the team lead's four sentences word for word. The `anything` job runs the product's own `answer_task`, so it scores what the Portal gets.
- **Code.** The Planner code of main at `53ecd934`.
- **Judge.** `claude-sonnet-5-5` for both models. It scores each `anything` reply from 1 to 5 for being proper, logical and useful. A 4 or 5 counts as useful.
- **Runs.** [Haiku](https://github.com/qj1e7/ai-agent-workflow-builder/actions/runs/43693206771) and [Sonnet](https://github.com/qj1e7/ai-agent-workflow-builder/actions/runs/43693208779), one run each.

## How to run it

```sh
gh workflow run evals.yml --repo qj1e7/ai-agent-workflow-builder --ref <branch> \
  -f models=claude-haiku-4-5-20251001 -f judge=gateway:claude-sonnet-5-5
```

Add `-f jobs=anything` to run only the new set. The report is on the run's page and in its `eval-results` artifact. To merge saved runs into one report, run `python -m evals.report out.md a.json b.json` in `agent-runtime`. The [bake-off README](../model-bakeoff/README.md) has the rest.

## The top failure patterns

1. **Help, small talk and vague asks come back crossed.** Both models read them as a question about what the Planner can do. Code then ticks only a clause that says "you can do" or "help", and crosses the rest. The person sees "Ask this on its own, and I'll answer it." about the sentence they just asked on its own, or "I didn't follow that". 30 of Haiku's 46 crossings and 25 of Sonnet's 43 start from that reading. Examples: "list me the steps to use this app", "Can you work with Jira?", "good morning", "help me with tickets".
2. **Haiku refuses ordinary writes as skipping a yes.** In 11 of its 12 false refusals on `anything`, and in 44 of its 64 golden `answer` failures, Haiku itself answered that the request skips an Approver's yes. Code never overrules the model's refusal, so the person sees it. Sonnet made this mistake 0 times. Examples: "Every weekday at 9, check LangGraph for new releases and raise a Jira ticket if there's a new one.", "Pause the morning new-ticket check and tell me what needs me", "Make the morning new-ticket check run on Mondays only". Every case that must be refused still was, on both models: 10 of 10 here, and 78 of 78 in the golden set.
3. **A condition becomes a can't.** No reading structure holds "if", "whenever" or "unless", so the condition comes back crossed. Sonnet, which doesn't refuse these, still gives a can't. Examples: "Raise a Jira ticket in MOCK whenever Redis has a new release", "Open an upgrade ticket if FastAPI has a major release", "Every Friday summarise closed bugs in MOCK into a ticket, unless there were none".
4. **A watch time without am or pm is crossed.** "Check LangGraph for new releases every weekday at 9" crosses the time even when the watchlist already checks weekdays at 09:00. Replaying the recorded reading with "9am" gives a plain watchlist answer. Only the crossed time shows, so the person sees no way forward.
5. **Questions about their own data miss the question lane.** "Has the FastAPI upgrade ticket been approved yet?" is read as a question about the Planner and crossed. "When did the stale bug follow-up last run?" gets the workflows list with the question crossed. "Which versions of LangGraph, Redis, FastAPI and n8n do we run?" asks which software to watch.

## What the rules cause, and what the model causes

- **The rules cause most of it.** Patterns 1, 3 and 4 fail the same way on both models, and the stronger model fixes only a few of them. That covers the crossing of a whole message (`parts_of` and the Portal's "I didn't follow that"), the missing condition structure, the "9" against "09:00" match, a can't with only crossed clauses and nothing to do next, and one refusal by code ("after the approver says yes", on both models).
- **The model causes the false refusals.** Pattern 2 is Haiku 4.5's answer to the skip question. Sonnet 5.5 never gives it on these sentences. The rule that code never refuses less than the model turns each over-flag into a refusal. The 7 November baseline ran on `azure_ai/claude-haiku-5-5` and passed 215 of 218. A Haiku 5.5 run on today's code would show whether the app's move to Haiku 4.5 explains this. That is a guess until it runs.
- **Pattern 5 is both.** Some misses start with the model's reading. Others come from which answers the code sends to the question lane.

## What these numbers can't tell

- **The judge's view of state answers is low.** In this run, the judge saw a placeholder for what needs you, the workflows list and the troubleshooter (15 Haiku and 16 Sonnet answers), where the Portal shows the person's own state. The fix is in the eval code. The rerun with it stopped when the gateway budget ran out. Leaving those answers out, the judge found 23 of 108 Haiku replies and 26 of 107 Sonnet replies useful.
- **The judge is also a contestant.** Sonnet 5.5 judged its own answers. Code writes most of the words shown, which leaves little room for self-preference, but not none.
- **One run per model.** The `anything` job sends the product's exact messages, so the gateway can answer a rerun from its store. This run says nothing about how much a model varies.
- **The golden `answer` job asks differently.** It sends the Planner's rules inside the user message, while the product sends them as the system message. The `anything` job uses the product's own path.
- **The expectations were set before the runs.** They stayed as written. For example, "Check LangGraph for new releases every weekday at 9" fails on its answer kind: its list did not include a can't with a watch offered instead, and the judge gave that reply a 4.

## Things a person needs to act on

- **The gateway budget is spent.** On 15 November the gateway answered 422, "Budget has been exceeded", with $33.28 used of $32. That stopped the two reruns. If the app uses the same key, its Planner falls back to the offline answer until the budget resets.
- **An email address reached two runs.** The gateway's budget error names the key's owner. Runs [43695785867](https://github.com/qj1e7/ai-agent-workflow-builder/actions/runs/43695785867) and [43695788034](https://github.com/qj1e7/ai-agent-workflow-builder/actions/runs/43695788034) hold it in their logs, page and artifacts. The eval now removes email addresses from errors. Deleting those two runs needs a person.
- **The key is a repository secret.** ADR 0032 and the bake-off README keep the eval keys in the `evals` environment, which only `main` may use. `AISG_API_KEY` is a repository secret, so a workflow on any branch can read it. GitHub created the `evals` environment on the first run, with no rules. Moving the key into the environment, with the `main` rule, would stop the branch runs this page relies on.
