# Prototype v2: what changed after usability testing

- **Date:** 27 Oct 2026
- **From:** prototype v1 (`docs/design/portal-routines/v1/`)
- **To:** prototype v2 (`docs/design/portal-routines/prototype.html`, and the shared link)

The findings came from two sources:
- **ChatGPT:** an independent evaluation of v1. The report is in [`2026-10-27-chatgpt-v1-evaluation.md`](2026-10-27-chatgpt-v1-evaluation.md).
- **Internal:** an automated first-time-user walkthrough of v1 by a separate AI tester.

Severity is as each source rated it. ChatGPT used its own scale (S1 critical to S4 low). The internal walkthrough used 4 = blocks the task, 3 = major, 2 = minor and 1 = cosmetic.

## Fixed in v2

## Fixed after the named-Approvers review

ChatGPT tested the named Approvers again later on 27 Oct and rated them 4.5 out of 5. The review is in [`2026-10-27-chatgpt-v2-approvers-review.md`](2026-10-27-chatgpt-v2-approvers-review.md). It asked for 3 fixes before operators see the prototype. All 3 are done, as well as one low-severity wording fix. The result is artifact version 10.

| Finding | Severity | What changed | Where to see it |
|---|---|---|---|
| While waiting for a yes, the approval panel said "Posted in CODESparks Support", as if it had already happened. | S2 | It now says "To be posted in CODESparks Support". The Confluence version had the same problem, and now says "To be added to the top of the Weekly summary page". | `run-escalated.png` |
| Too many approval settings at once. | S3 | Only "Asked first" and "Backup" show at first, with the whole rule in one sentence below them: "Bob is asked first. If Bob hasn't answered after 4 working hours, Siti is asked too. If nobody says yes within 2 working days, it stops and nothing changes." The 2-Approver option, the two waits and the working hours are under "More approval options". | `new-routine-schedule.png` |
| After a request had stopped, "Change who approves" still said a request was waiting. | S4 | The note depends on the state. While a request waits, it says the request keeps its people. After it stops, it says the change starts with the next run and the stopped test run isn't started again by itself. | `routine-approvers.png` |
| Step 4 named CODESparks Support twice in one sentence. | S4 | The sentence says who is asked for a yes. Below it, "Approval requests" and "Result" are listed separately. | `new-routine-review.png` |

## Names changed after the reviews

Later on 27 Oct the team changed four names in the prototype. Both ChatGPT reports above used the old names, because those were the names they saw.

| Old | New | Why |
|---|---|---|
| Routine | Workflow | It matches the project's name, and suits multi-step work like the access review. "Workflow" also means n8n's and Jira's workflows, so the glossary says to write "n8n workflow" and "Jira workflow" for those. |
| Room lead | Planner | The "room" no longer appears anywhere in the design. The agent reads the request, says what it understood and plans the work. |
| Portal (header name) | AI Workflow Builder | "Portal" was never chosen as a name, only a description of the web app. It stays as the internal name. |
| Software (menu and page) | Software watchlist ("Watchlist" on the phone tab bar) | "Software" named the list but not what happens to it. "Software updates" was tried first, but the team chose one name shared by the app, the glossary, the code (`watch.py`) and the product brief. The page's first line says what it does: new releases are checked on a schedule, and upgrade tickets go out in one approval. |

The screenshot file names are unchanged, so links keep working. For example, `routines.png` now shows the Workflows page.

## Added at the team's request, after the reviews

Neither review asked for these, so neither has been evaluated yet.

| What | Why | Where to see it |
|---|---|---|
| **Agent library** is its own menu item, not part of Settings. | The agents are what the product is about, so they shouldn't be hidden in Settings. | `agent-library.png` |
| **Agent details and plain-English changes.** Clicking an agent shows how it works, its tools and rules, where it's used and its versions. An Operator says what should change, the Planner redrafts the steps, and the platform checks the draft before it can be saved as a new version. Requests to skip a yes are refused. A request that needs a new tool leads to Tools, and a new system goes to the team. | The team wanted the library to be useful, and wanted agents changed by describing the change rather than editing it by hand. It stays inside ADR 0023: the AI drafts, and a person saves. | `agent-details.png`, `agent-change.png`, `agent-change-refused.png` |
| **Settings has four tabs.** Connections (each system's key, when it expires, Test and Replace key, and a Home warning 14 days before a key expires); People and roles (Approvers need a second Approver to confirm them, and someone named on a workflow keeps the role); and AI usage (questions, estimated cost, a monthly limit and questions by workflow). | The team chose these from suggestions, so that a non-technical person can fix an expired key, add a colleague, and keep the AI cost in check. | `settings-connections.png`, `settings-people.png`, `settings-usage.png` |
| **Settings is now only the AI model, with a field for the API key.** Choose a provider, paste the key, Connect, pick a model, then Test and save. The key can't be read back, and the page shows only its last 2 characters. A new address waits for an Approver, and every change is in the change history. The agents, tools and practice systems panels are gone: the Agent library has its own tab, and Teams has its header button. | The team asked for a place to enter the model's key, as ADR 0022 proposes, and wanted nothing else repeated in Settings. | `settings.png` |
| **A clearer security risk.** A tool with a known vulnerability gets a card at the top of the Software watchlist. It answers four questions: how serious (10.0 out of 10, with a bar), whether attackers are using it, how many known vulnerabilities, and the fix. "See all" lists each one in plain English, and the sources follow. The urgent ticket in the approval panel shows the same answers. | One sentence packed in the count, the sources, the CVE number, the score and CISA's list, so an Operator had to read it twice. | `software.png`, `security-risk.png`, `run-approval.png` |
| **Tools** is a second tab in the Agent library. Each tool shows whether it's working, with "Check it works"; what it can and can't change; which agents use it; and its recent changes with who said yes. Tools and agents link to each other. An Operator can ask for a new tool in plain English: the Planner checks the existing tools, drafts a new one from a connected system's published API for an Approver's OK, or sends a new system to the team. | The team wanted a Tools section that connects with the agents. The tool status gives non-technical staff a way to tell what broke, and the tool drafting shows the tool card idea, which still needs an ADR. | `agent-library-tools.png`, `tool-details.png`, `tool-draft.png`, `tool-ask.png` |

## Not changed, and why

| Finding | Source | Reason |
|---|---|---|
| Approving some tickets in a check and not others | ChatGPT, in both reviews | ADR 0019 chose one decision per check for the first version. Changing that needs a new decision. |
| Changing what a routine does after it's on (which tickets, what it does, where it goes) | ChatGPT S3, in the named-Approvers review | Not done yet. It would run the understanding check again on a live routine, and show the old and new versions side by side before replacing it. It's the next candidate for the prototype if the team wants it. |
| Phone view of the shared link is cramped | ChatGPT S3 | This comes from the claude.ai page around the prototype. The prototype file itself adapts to phones, with a bottom tab bar. For phone testing, use the file or a static host. |
| Adding software still needs its GitHub project | Internal (3) | Looking up a project by name needs an AI model or a search service. That's a new external dependency, so it needs an ADR. |
| "Check now" and "Not now" show a message only | Handover | These are simulated in the prototype. |

## How v2 was checked

- **Every changed flow was clicked through** in a browser (Chromium). That includes ChatGPT's exact request from the S1 finding, which v2 now reads as asked: Friday at 16:00, open tickets with no update for 14 days, a summary posted in Teams.
- **Named Approvers were clicked through too:** choosing people and the 2-Approver option; errors for a missing choice; a backup asked after the wait; a request that stops with nothing written; a request that stops before a daily routine's next run; an Approver who isn't named being refused; and changing who approves while a request waits.
- **The browser console showed no errors.**
- **The screenshots were retaken** from v2.
- **v2 hasn't yet been re-evaluated independently.** The next step is to give ChatGPT the updated handover (`docs/handover/PROTOTYPE_HANDOVER.md`) with the same instructions, and compare the two reports.
