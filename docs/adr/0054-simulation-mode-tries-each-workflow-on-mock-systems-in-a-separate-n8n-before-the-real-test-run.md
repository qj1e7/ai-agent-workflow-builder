# Simulation mode tries each workflow on mock systems in a separate n8n, before the real test run

On 23 and 24 Nov 2026 the team lead asked for Simulation mode as an upgrade to the Check step (ADR 0053), with 2 to 4 options and this ADR before any code. The proposal: before a workflow version is turned on, it runs through a few short scenarios against mock systems, in a separate n8n that holds no real key. The AI writes the scenarios and explains the results. Code builds the mock setup, runs the scenarios and decides pass or fail. One real test run, which writes nothing, stays the final check.

It builds on ADR 0044 (the test run), ADR 0045 (the node allow list and pinned output), ADR 0051 (the drafter and the digest) and ADR 0053 (Describe, Check, Turn on). It adds a new service, so `AGENTS.md` asks for this ADR. It doesn't change the approval gate, the safety checker, the test run or the digest. ADR 0055 ("Fix it for me") uses it to prove a fix.

Sentences in quotes marked "(needs OK)" are proposed words for people to see. They need the team lead's OK.

## Words used here

These terms are new. They go in `GLOSSARY.md` once this ADR is accepted.

- **Simulation.** Runs of a copy of one workflow version in the simulation n8n, one run for each scenario. Nothing in a simulation can reach a real system. A simulation is not a run: it isn't in Recent runs, and it never counts as a test run.
- **Simulation n8n.** A second n8n, on the same pinned image and node pack as the platform's n8n. It has only mock keys, and it reaches only the mock systems and the simulation gateway.
- **Scenario.** One situation a workflow should handle, written as data: what each mock system answers, and what the Approver says. There are six kinds: happy path, nothing new, source not found, timeout, Approver says no, and odd data.
- **Mock setup.** The mock keys, mock systems and pinned output that code builds for one version from the node allow list.
- **Recorded sample.** A real answer from a system, scrubbed of personal data, that a scenario replays or varies.
- **Coverage gap.** A block or branch that no scenario reached, or a scenario kind that applies to the workflow but has no scenario. Code finds it.

## Context

**What the Check step proves today.** In Check the person reviews the card. Turn on then runs a test run and turns the workflow on if it passes (ADR 0053). The test run runs n8n's draft of the workflow by hand, through `POST /rest/workflows/{id}/run` from Start from the Portal (`run_draft` in `orchestration/n8n.py`, and `orchestration/n8n_starts.py`). It doesn't start if the draft changed or a notice block has no pinned output. It reads real data and stops at the approval gate (`stops_at_gate` in `orchestration/service.py` answers `test_passed`). It posts nothing and writes nothing. So it proves the happy path on today's data. It can't show what the workflow does when nothing is new, the source is gone, a system is slow, the data is odd, or the Approver says no. Those are the cases that stop runs on day 100.

**What n8n gives us.** n8n 2.42.6 uses pinned output (`pinData`) only in a run by hand or in evaluation mode (`resolvePinData` in `workflow-runner.ts`, and `webhook-helpers.ts`). n8n's docs say pins are not for production runs. Pins already keep a test run from posting (ADR 0045, amendment 7, and ADR 0051, section 4), and they work live in test runs (`e2e/tests/test_n8n_keys.py`). Pins are part of the approval digest (`orchestration/version_digest.py`), so a pin added for a scenario would change the version an Approver sees. A pin replaces a block's output. It can't make the block fail or time out.

**What mocks we have.** `deploy/compose.e2e.yaml` runs mock GitHub (port 8200), mock Confluence (8400), the mock model (8300) and mock Slack (8500). Mock Slack sits under the DNS alias `slack.com` with its own CA, because n8n's Slack block always calls `https://slack.com`. `scripts/e2e.sh` and CI start them. platform-api has the practice Jira when `JIRA_BASE_URL` is unset (ADR 0035), a Teams stub (`orchestration/teams.py`) and mock sign-in. The agent runtime has recorded model replies (`agent-runtime/evals/cases/recorded_replies.json`). n8n reaches a mock through a credential's address, as `wab-github-read` does. The runtime reaches one through its env addresses.

**What we don't have.** There is no test n8n and no test project. The platform keeps its workflows in the n8n owner's own project (`platform_project` in `orchestration/n8n.py`). On n8n's free edition a credential can't be shared across projects, each member has one personal space, and a workflow in the owner's project can use every key there is (ADR 0045, amendment 6). Our blocks call only one address, `WAB_API_URL`, with `WAB_NODE_KEY` (`n8n-node-pack/README.md`). Both are set on the container, so one n8n has one of each. HTTP Request and Code reach whatever n8n can reach (ADR 0051).

## Decision

We recommend option C: a separate simulation n8n with only mock keys. Each part says whether code or the AI does it.

1. **Simulation runs in Check, before the real test run.** Once the safety checker has graded a version, code runs it through its scenarios in the simulation n8n, in the background. The Check card shows the results first, for example "Tried 6 cases on practice systems: 5 passed." (needs OK). Turn on then runs the one real test run, which writes nothing, as today (ADR 0053). A passed simulation never turns anything on and never stands in for that test run. A failed scenario doesn't block Turn on: the card leads with what failed and why, and the person decides, because a mock can be wrong and the real test run is the check. The team lead may prefer that a failed scenario blocks Turn on until the person accepts it.

2. **The simulation n8n (code).** It runs the same pinned image, node pack, node allow list and bootstrap as the platform's n8n, with its own database and encryption key. Code makes only mock credentials there. It holds no real key and no write key. Its network reaches only the mock systems and the simulation gateway. On a laptop and in CI that is a compose network with aliases, as mock Slack has today. On Azure it is its own Container App with no route out (spike item S6). Its `WAB_API_URL` points at the simulation gateway, with its own `WAB_NODE_KEY` and `WAB_START_SECRET`.

3. **The simulation gateway (code).** A small part of orchestration, with its own routes and tables, kept apart from runs. It answers our blocks in the simulation n8n as the real API does, with five differences. It records simulated runs apart, so none shows in Recent runs or in the activity log as a run. Our Read block gets the scenario's data, since our blocks call only `WAB_API_URL`. Our Agent block runs on the mock model or recorded replies, never on a paid model, so a simulation tests the workflow around the agent, not the agent's own judgement. Ask for a yes gets the scenario's answer, yes or no, and asks nobody. Every write is refused, as the write gateway refuses a test run's write, and Tell sends nothing. It holds no Jira, Teams or Slack key.

4. **Code builds the mock setup from the node allow list.** For each of n8n's own blocks in the version, its row in `node_classes.json` gives its system and its class (read, notice or write). For a system with a mock (GitHub, Confluence, Jira through the practice Jira, and Slack), code makes a mock credential of the block's own type that points at that mock. For a block whose system has no mock, and for HTTP Request and Code, code pins the block's output from the scenario's data. The simulation runs by hand, so the pins apply. Such a block can't play "source not found" or "timeout", so those pairs show as "Not tried" (needs OK), never as passed. A block the class file doesn't class is not simulated, and the card says so. The model never builds or changes the mock setup.

5. **The AI writes scenarios, and code checks and grades them.**
   - **Which kinds apply (code).** Code picks the kinds that fit the version. A version with no Ask for a yes gets no "Approver says no". A version with no outside read gets no "source not found" or "timeout".
   - **The scenarios (AI).** The scenario writer, a model in the agent runtime, writes one scenario for each kind that applies. A scenario is data in a schema that code owns: for each mocked system, which recorded sample it serves and how (as recorded, varied, empty, not found, or too slow), and the Approver's answer. The writer picks and varies recorded samples, for example a version string with a suffix, an empty field, or very long text. It can't add a block, a system or a key. Code refuses a scenario that names one the version doesn't have.
   - **Pass or fail (code).** Code holds the expected outcome for each kind. The happy path reaches the yes with the expected change. Nothing new ends as Nothing new and proposes nothing. Source not found and timeout stop with a reason the troubleshooter can name, and never write. Approver says no ends as Declined with nothing written. Odd data ends in one of those, never in a failure with no reason. Code reads each simulated run's events and n8n's execution data, and decides pass or fail.
   - **The explanation (AI).** The model explains each failure in one plain sentence. Its words help the reader. They are never the verdict.
   - **Without a model.** Code's own six scenarios, built from templates, still run, with the recorded samples as they are.

6. **Recorded samples are scrubbed first (code).** A sample comes from a mock's own fixtures, or from what a read block returned in a real run of the same workflow (n8n's execution data). Before code stores one, it keeps only the fields on an allow list for that system's answer, such as `tag_name`, `name`, `published_at`, `html_url`, `prerelease` and `draft` for a GitHub release. It replaces every other text field with a fixed fake value. Names, emails, user and account ids, avatars, and text that people wrote are never kept. Key shapes are masked, as traces are (`monitoring/masking.py`). Until the DevNet move, samples come only from open-internet sources and the practice Jira, never from NCS data (ADR 0050). It is an allow list, not a deny list, because deny lists leaked in four review rounds on 18 Nov.

7. **Refining a new workflow's Check.** For a drafted workflow (ADR 0051), the coordinator in ADR 0055 runs the same loop it runs for a fix.
   - The drafter drafts, code checks it, the simulation runs, and code reads which scenarios failed and why.
   - The coordinator sends one targeted follow-up. Either the drafter refines the same draft with that evidence ("change only block X"), or the scenario writer adds a scenario for a coverage gap that code found. Code finds gaps from n8n's execution data (which blocks ran in each scenario) and from the kinds that apply.
   - The loop has ADR 0055's step limit, cost cap and timeout, and each round counts toward them. It stops early when a round makes no progress or widens the change.
   - Every round goes in the activity log and the live activity view. The activity log keys events by run today, and a Check has no run, so its rounds need a stream keyed by the drafted workflow (PR 8 settles its shape).
   - When all scenarios pass, the person sees the final draft with the rounds tried, and Turn on runs the one real test run.
   - A workflow the Planner builds from our own blocks is simulated too, but not refined. Its layout is our tested code, so a failure there is a bug for the team, reported to support.

8. **What stays the same.** The real test run, its pins and its refusal rules (ADR 0044, and ADR 0045, amendment 7). The safety checker and its grade. The digest: the simulation runs a copy in the simulation n8n, so a scenario's pins never touch the version an Approver approves. The approval gate. Nothing in a simulation is ever a write to a real system.

## Considered options

- **A. Pinned data on the test run's manual path, in the platform's n8n.** Code copies the version, pins each outside block's output with scenario data, and runs the copy by hand through the test run's path (`run_draft` with `triggerToStartFrom`). For: no new service. The test-run path, pins and `stops_at_gate` exist and work live. Against: a pin can't fail or time out, so "source not found" and "timeout" can't be played. The test run stops at the gate, so "Approver says no" needs a second path through the real gate. The copy sits in the owner's project, where a workflow can use every key there is, and every sweep (versions, keys, holds) would see it. Pins are in the digest, so they can't go on the version itself. Unknown: whether a pin on one of our blocks keeps the run linked (Record the run's nonce), whether pins work with `triggerToStartFrom`, and what evaluation mode adds. Kept inside C, for blocks with no mock.
- **B. A separate n8n project in the same instance, with mock credentials.** On the free edition that is the personal space of a simulation account, as staff spaces are. For: no new container. Against: one container has one `WAB_API_URL` and one node key, so our blocks there would call the real API, and Ask for a yes would reach the real gate. n8n's own blocks with a fixed host, such as Slack, can be pointed at a mock only by a DNS alias, which would catch the live workflows too. HTTP Request and Code reach whatever the real n8n reaches. The credential sweep, holds and staff guards would each need an exception for that space. One mistake puts a scenario next to real keys.
- **C. A separate n8n instance with no real keys and only mock credentials (recommended).** For: nothing in it can reach a real system or the real gate, even when a scenario or a fix is wrong. It can play all six kinds, since a mock can answer "not found" or answer slowly, and the gateway can say no. It reuses the e2e mocks and the Slack alias that CI already proves. It runs the same image, so a pass says something about the real n8n. Against: one more container and database to run, deploy and keep on the same pin, a mock to build for each new system, and the gateway is new code.
- **D. Our own interpreter that plays the workflow without n8n.** For: fast, needs no n8n, and we control it fully. Against: we would rebuild n8n's expression language, item pairing, error settings and each block's behaviour, and it would drift from the pinned image. It would prove our model of n8n, not n8n. Rejected.

## Consequences

- **Running cost.** One more n8n container and its database, with the mocks deployed beside it (today they run only in CI and on laptops). Deploying it changes cloud resources, so it waits for the team lead.
- **Model cost.** Writing scenarios and explaining failures are paid calls. A guess before any measurement: about 3 cents to write a version's scenarios and 1 cent for each failure explained, on Claude Sonnet 5.5 at ADR 0051's prices. In a fix they count toward ADR 0055's cap.
- **Upkeep.** Each new system a workflow can reach needs a mock. Until it has one, its blocks get pinned output only, and its "not found" and "timeout" show as not tried. Both n8n instances move together when the pin moves. `scripts/pack-smoke.sh` and `pin_check` already run against the one image they share.
- **DevNet.** The simulation n8n needs no outside network, so it moves easily.
- **ADR 0055** depends on this ADR, its spike, and PRs 2 to 5.

### Before acceptance: a live spike

These are unknown on `origin/main` and need a live spike, with no paid model calls:

- **S1.** A second n8n from our image boots with our node pack and bootstrap, with only mock credentials, on its own compose network, and `scripts/pack-smoke.sh` passes against it.
- **S2.** For each system on the allow list today, a credential of n8n's own type can point at our mock (GitHub's server address, Jira's and Confluence's domains), or it needs a DNS alias and CA, as Slack does.
- **S3.** Our blocks work against a simulation gateway: Start from the Portal with its own start secret, Record the run's link, Ask for a yes answered no, and a refused write.
- **S4.** Pins work in a run by hand with `triggerToStartFrom` in the simulation n8n, on a read block and on one of our blocks, and the run stays linked.
- **S5.** A timeout can be played quickly. Find whether a mock that holds or drops the connection makes n8n's block fail as a real timeout does, within the block's own timeout and retries.
- **S6.** On Azure, a Container App can be kept from reaching anything but the mocks and the gateway. If it can't, isolation rests on holding no real key, and this ADR says so.
- **S7.** n8n's execution data shows which blocks ran in each scenario, so code can find coverage gaps.

What the results change in this ADR:

1. **Section 4.** Confluence needs no mock key: n8n's own Confluence block is not on the allow list, so a Confluence read comes only through our Read block, which the gateway answers. Teams, Outlook and Gmail need no mock while they are notice-only, because a run by hand pins every notice block.
2. **Sections 4 and 5, "source not found" and "timeout".** A faithful timeout of n8n's own block takes 300 s for each try, which would use up most of ADR 0055's 20 minutes. So a mock plays a timeout by dropping the connection, or by holding while the simulation's copy carries a short time limit. In the second case code grades a `canceled` run, and names the held block from the mock's own record. For our blocks, the gateway answers "not found" or "timed out" at once.
3. **Section 5, grading.** n8n runs the error workflow only for runs it did not start by hand. A simulation runs by hand, so code reads every failure from n8n's execution data, never from Report a failure.
4. **Sections 5 and 7, coverage gaps.** The refused write ends the run, so a block after Make the approved changes, such as Tell, never runs in a simulation. Code reports it as not tried for that reason, or the gateway answers a write with "would have made", as Tell answers "would have sent" (PR 3 chooses). Code also keeps its own list of the blocks it pinned.
5. **Section 2, Azure.** The simulation n8n, the mocks and the gateway's address need their own Container Apps environment and subnet. Isolation rests on holding no real key. The outbound service tags that subnet must allow, `AzureContainerRegistry`, `Storage.<region>` and `AzureFrontDoor.FirstParty`, also cover other Azure customers' endpoints, so on Azure isolation still rests on holding no real key. PR 2 and PR 3 choose whether the gateway runs in that environment or stays in platform-api, where the simulation's node key would be the only guard on the real API.

#### What PR 3 chose, 24 Nov 2026

- **Where the gateway runs.** As its own service in the simulation's network: `gateway` in `deploy/compose.simulation.yaml`, and `sim-gateway` in the simulation's Container Apps environment. It runs platform-api's image with its own command, and mounts platform-api's router for our blocks, so each block gets the same answers and refusals. It is not a mode of platform-api, which holds real keys and the real database, and which the platform's n8n reaches.
- **Writes.** Every write is refused with 403 "A simulation never writes.", and the gateway keeps what it would have written. So a block after a write never runs in a simulation, and PR 5 reports it as not tried for that reason (point 4 above). A write set to go on after a failure (`onError`) is the exception: n8n passes the refusal on, so the blocks it leads to run (`scenarios._after_writes`, added 25 Nov 2026).
- **Records.** The gateway keeps its simulated runs in memory, not in tables, because the simulation's own PostgreSQL is in memory too. A restart of either forgets the simulation under way, so PR 5 must start it again.
- **Starts.** The gateway issues each start's nonce for one scenario. The driver's routes, a start and a record read, are signed with the simulation's start secret. The simulation n8n's own environment holds that secret, because Start from the Portal checks a start with it. A workflow under simulation still can't read it to start or read a simulated run: n8n keeps expressions from reading its environment (`N8N_BLOCK_ENV_ACCESS_IN_NODE`), Code runs in the external task runner, which holds none of n8n's settings, and the mock setup refuses HTTP Request and Code.

#### What PR 4 chose, 24 Nov 2026

- **Where the mock setup runs.** In the gateway, as a third signed route, `POST /simulation/v1/copies`. It takes a version and makes its copy in the simulation n8n, through that n8n's own owner and API key, so platform-api never holds them.
- **The class file decides.** Each of n8n's own blocks for a system says how a simulation stands in for it (`simulated` in `node_classes.json`): a mock (GitHub, Jira, Slack) or pinned output, with why (Teams, Outlook, Gmail). Our blocks call the gateway, and n8n's other blocks run as they are. Anything else is refused, and nothing is made.
- **Mocks that run.** Mock GitHub, through its key's server address, and mock Slack, under the name `slack.com` with a key the stack makes up at each start. No mock Jira runs in the simulation yet, so a Jira block is pinned, with that reason, until one does (`MOCK_JIRA_URL`).
- **Keys.** The copy names only the mock keys the gateway makes, each of a type the platform's own key for that system has, with made-up values. Every key the version names is left out.
- **Pins.** Only a block with no mock is pinned: from the scenario (PR 5), else from the version's own pin, else with an item that says it was pinned. Each block's mode is in the answer, and the pinned ones are listed as not tried.

#### What PR 5 chose, 24 Nov 2026

- **Where a simulation runs.** In the gateway, as a fourth signed route, `POST /simulation/v1/simulations`. Each scenario runs on a copy of its own, since its pins are part of the copy, and the copy is deleted once it is graded, whatever happened. One simulation runs at a time, since mock GitHub plays one scenario at a time.
- **The schema.** For each block that reads a source, how it is served: recorded, varied, empty, not found or too slow. For each Agent block, a recorded reply, or one that is too slow. The Approver's answer follows from the kind. A block a scenario leaves out is served as its kind's template serves it. Code refuses a block, sample or play that doesn't fit the version or the kind. "Odd data" applies only when an allow list covers a read, since code has nothing else to vary.
- **Timeouts.** Mock GitHub drops the connection, which stops n8n's own GitHub block in about a second, in words the troubleshooter names (spike S5). The gateway answers our Read "The source did not answer in time." at once. Mock GitHub also serves a scenario's releases, or answers not found, for every repository, until the simulation sets it back.
- **Grading.** Each kind's expected outcome is as section 5 says. A timeout at one of n8n's own blocks passes only when the troubleshooter names the stop. A write with no yes fails any scenario. A pinned block never counts as run. A scenario no block can play, such as a timeout where every read is pinned, is not run, and shows as not tried.
- **Recorded samples.** Allow lists for four answers: a GitHub release, our Read's release, our Read's Confluence page and a Jira issue (`recorded_samples.py` states each). Every other field is left out. A value kept must fit its shape: a version, a time, a flag, a count, a Jira key or one of a few fixed words. Text, links and page ids become fixed made-up values, a release's name is kept only when it is its tag, and key shapes are masked. The gateway keeps samples in memory for one simulation, and scrubs any it is sent. Keeping real runs' samples between simulations comes with the PR that sends them.
- **Pins.** A copy never takes the version's own pinned output, which may be what a real run read. It takes the scenario's, from a scrubbed sample, or an item that says it was pinned.

#### What PR 6 chose, 24 Nov 2026

- **Picks, not words, for both calls.** The scenario writer and the explainer answer in fields the model picks from what code offers, as the troubleshooter does since #367. No words the model writes reach anyone.
- **What the writer is offered.** A fifth signed route, `POST /simulation/v1/plans`, answers a version as a simulation sees it: each block's role, the plays a simulation can make of it and the variations its answer takes, the kinds that apply, and the samples, scrubbed. It makes nothing. The writer gets only these facts.
- **What the writer can write.** One closed shape: for each kind, how each read is served, which sample and which variations, and which Agent blocks are too slow. A reply that adds a system, a key, a write, items of its own or any words doesn't parse, and is refused. The runtime then checks only that every name is one it was offered: each kind once, and the reads, samples and Agent blocks. Whether a play fits its kind is PR 5's own check, `check_all`, with no second copy. The driver sends the written scenarios with `fall_back`, so any refusal runs code's six templates in their place, and the answer says so (`scenarios_from`, `refused`). Without a model the templates run, as before.
- **The explainer picks, and code writes the sentence.** For each failed scenario it picks the block, a kind of failure (stopped with no reason, went on, ended before the yes, other changes, kept from ending, or unknown), the block whose play led to it, and at most one name from what happened, by the troubleshooter's rule (`named_in`). Code leaves out a note whose picks aren't the scenario's own facts, shows a kind the facts give no sign of as unknown, and drops any words beside the picks. Since no free text is kept, the troubleshooter's word guard has nothing to check. The grade stays the verdict, and a failure with no note keeps code's own words. For this, a grade now carries how the run ended, where it stopped and how the scenario played each block, and a write with no yes, or with changes left out, ends as a wrong write.
- **Off unless a caller asks.** `SimulationModel` in platform-api is wired as the troubleshooter's cause finder is, and asks the runtime only when a caller asks, with the model connected in Settings. The Check card (PR 7) is its first caller.
- **Limits.** The writer has 30 seconds, a prompt of at most 30,000 characters and an answer of at most 3,000 tokens. The explainer has 15 seconds, 12,000 characters and 1,200 tokens, and explains every failure of a simulation in one call. Nothing is sent when the prompt holds the shape of a key. So a simulation costs at most 20 cents at the dearest model the evals price, Claude Opus 5.5, and at most 7 cents on Claude Sonnet 5.5. A test holds the cap.
- **Evals.** `scenario_writer` and `scenario_explainer` in `agent-runtime/evals`, each case with a recorded reply that the tests replay with no paid call. The red-team cases add a block, a system or a key, try to write, plant an instruction in a sample, a block's name or what happened, blame a person, or give advice. A run on a real model waits for the team lead.

#### What PR 7 chose, 24 Nov 2026

- **When it runs.** Once the checker has graded a drafted revision with nothing still needed, made by the drafter, an answer or Done in n8n, platform-api sends it to the gateway's `POST /simulation/v1/simulations` in the background (`orchestration/simulation_driver.py`). A revision that still needs a setting isn't tried, since its blanks would fail every case.
- **By digest.** Each result is kept in `builder.drafted_simulations`, by the drafted workflow and the revision's digest. The running row goes in the same transaction as the revision, and the simulation starts once it commits, so a poll never reads a new revision as untried. The card reads only the newest revision's digest, so a changed version starts a new simulation and never shows an older result. Nothing here writes a run or an activity event.
- **The card.** It leads with the count, such as "Tried 5 cases on practice systems: 4 passed.", then each case, what failed first: code's Expected and What happened, then the AI's note as help. A case no block can play reads "Not tried" and never counts as passed. A failed case blocks nothing, as section 1 recommends. The card says so, and Turn on still runs the real test run.
- **Honest states.** Unavailable where platform-api has no `SIMULATION_URL`, and the card says "Simulation on practice systems isn't available here." Running, "Trying it on practice systems.", with each case's limit from `WAIT_LIMIT_SECONDS` (2 minutes). A try past the whole limit, six cases of 2 minutes plus 2 minutes, counts as ended: it shows as not finished, never as running. A revision never tried offers Try it now. When the practice systems didn't answer, or a try didn't finish, an Operator can try again. Once shutdown begins, no new simulation starts.
- **The registry.** `workflows.simulate` is planned in the runtime's registry ("Practice systems aren't set up here."), with no short words, so the chat's What I can do card is unchanged. It is Ready only where platform-api turned it on (`ready_here`). The capabilities view and the Planner's prompts, its briefing, the free reply and the verifier, all follow that one rule. The reply guard keeps holding a reply to the registry, so it can only say less than it could.
- **No paid call by default.** `SIMULATION_MODEL` is off, so code's six templates run and no model is asked. On, the scenario writer and the explainer run as PR 6 built them, at most 20 cents for each simulation. Turning it on waits for the team lead's budget.
- **Not linked yet.** No environment links platform-api to the gateway today. The simulation stack shares no network with the platform's (`deploy/compose.simulation.yaml`), and Azure has `enable_simulation = false`. So every environment shows "isn't available here" until a follow-up links them. That changes the isolation check and the network rules, so it waits for the team lead.

Outside this ADR: no real workflow has a time limit of its own (no `EXECUTIONS_TIMEOUT` and no `executionTimeout`), so a hung source holds a real run for 300 s for each try of the block. Whether real workflows get a shorter one is for the team lead.

#### What the link chose, 24 Nov 2026

The team lead chose to link platform-api to the gateway on a laptop and in CI only, so the Check card shows real results there, with only the gateway in reach from the platform's side. Azure stays unlinked: `enable_simulation` stays false, the Terraform is unchanged, and nothing is deployed. This replaces "Not linked yet" in PR 7's note for laptops and CI.

- **One small network, made by the simulation.** `deploy/compose.simulation.yaml` adds `link`, an internal network with the gateway alone on it, under the name `simulation-gateway`. The platform's `deploy/compose.simulation-link.yaml` joins platform-api to it, and changes nothing else. platform-api keeps its own network. The simulation n8n stays on the simulation's networks, so it shares none with platform-api, PostgreSQL, the platform's n8n or the agent runtime. The gateway shares one with platform-api alone, so PostgreSQL, the platform's n8n and the agent runtime are out of its reach. We chose this over putting the gateway on the platform's network, which would put PostgreSQL and n8n in its reach, and over a port on the host, which the platform's n8n could reach too.
- **The gateway could open platform-api's port.** A network goes both ways. The gateway holds none of platform-api's keys, makes no call to it, and calls only the addresses in its own settings, so a workflow under simulation can't send it there. On a laptop, anything on the host can open that port too.
- **The start secret is the one value both sides hold.** `deploy/make-env.sh` makes `SIMULATION_START_SECRET` in `deploy/.env`, so each laptop has its own and each CI run makes a new one. The link file gives it to platform-api, and `SIM_LINK=<platform's project> scripts/simulation.sh up` gives the same value to the simulation n8n and the gateway as their start secret. Nothing prints it. platform-api and the gateway refuse one shorter than 32 characters, and make-env makes 64. It opens only the gateway's signed routes and starts in the simulation n8n, and platform-api uses it for nothing else. Every other simulation key is still made up at each start, and the gateway still holds no real key and no database address.
- **The check proves it from inside the containers.** With `--platform`, `scripts/simulation_isolation.py` tries every address of the linked platform's platform-api, PostgreSQL, n8n and agent runtime from the simulation n8n, and every one but platform-api's from the gateway. It tries the gateway's addresses from the platform's n8n and agent runtime, and the gateway's name from platform-api, which must answer. Each container that probes must reach a service of its own stack, so a blind probe can't pass. It allows the start secret only as the start secret of the simulation n8n and the gateway, and only the named platform's platform-api on the link. It also reads the link file, and fails if the file changes more than platform-api's networks and its two settings. Linked or not, it tries the host from the simulation n8n and the gateway at each simulation network's gateway address, on 8000, 5678, 5432 and each port a linked platform publishes, because `host.docker.internal` never resolves on an internal network.
- **CI.** The `simulation-link` job runs `E2E_SIMULATION=on scripts/e2e.sh`. It starts the simulation, then a whole platform stack with the link file. It drafts the release check with the mock model, answers its question, and waits for the card's result from code's six templates, with no model asked (`e2e/tests/test_practice_systems.py`). Then it runs the check on both stacks. On a laptop on 24 Nov the card read "Tried 6 cases on practice systems: 6 passed." about 25 seconds after the answer, and the check tried 19 addresses between the stacks, each as expected.
- **Order.** The simulation makes the link, so it starts first, and platform-api leaves the link before the simulation goes down. `scripts/simulation.sh down` stops and names the unlink command while platform-api is still on the link. `deploy/README.md` has the commands for the `wab` stack.

#### What PR 8 chose, 25 Nov 2026

PR 8 builds section 7 on ADR 0055's coordinator, scope check, reach and ledger, with only what differs for a draft.

- **Offered, never automatic.** A refinement makes paid calls, so an Operator asks for it with Refine it (needs OK), as only they set workflows up. It is offered only where `SIMULATION_MODEL` is on and a model is connected, which the drafter runs on, once the newest revision's try is done with a failed case or a block no case reached. A try now keeps each failed case's block and ending, and the blocks no case reached. A try kept before this PR has neither, so it offers nothing. Without the model the card shows the simulation as before.
- **The same coordinator, for a draft.** `RefineRequest` sits beside `FixRequest`. There is no stopped run, so there is no troubleshooter, no `find_cause` and no replay of the stop. Round 0 is the draft as the Check tried it, and the coordinator simulates it first. The failed part is code's: the blocks where a case failed on round 0, which grows as more cases run on it. A draft asked for before anything failed, or for a block where nothing failed, is refused. The limits, the no-progress and widening stops, the reach check and the cost count are a fix's.
- **Done, as code decides.** As for a fix, without the replay. Round 0 may be handed in unchanged only when every case that applies passes on it and a case reached each block the Check didn't. Then nothing new is kept, and the card says so.
- **The Scenario writer can aim at a block.** This closes the gap #375 left. Asked to cover blocks, the writer gets each one with the blocks that lead straight to it, and writes one to three cases of kinds that apply. platform-api names each by how it plays, and the coordinator keeps only one that plays the version differently from every case it holds. One that brings nothing new ends the fix or refinement for no progress. No answer, as when the writer timed out, has no calls left or has no model, is a refused call, so a fix or refinement that can already hand in still does. Without the model, code's templates can't aim, so an ask to cover brings no answer. A fix or a refinement may now ask the writer 3 times.
- **Its events, by the drafted workflow.** A Check has no run, so a refinement's events are kept by the refinement (`builder.drafted_refinement_events`): a fix's own kinds and data, under a fix's rules but the run being stopped. The Check card shows each round as it lands. The run-keyed live activity view doesn't show them. Its id has a fix's shape, and its token is signed for a refinement, so it never opens a fix's routes, nor a fix's token its routes.
- **The result is a revision, checked like any.** platform-api keeps the refined plan as the drafted workflow's next revision, made by code with no model, on the same card. Only while the refinement runs and the revision it refines is still the newest draft, with no setting changed, the change inside the blocks where a case failed on round 0 as platform-api's own simulation graded it, a simulation here that every case passed, and the safety checker's grade of safe. Then it goes through the normal Check: its grade, its own try on practice systems, and a set-up approval before it is set up. The person who asked is its asker, so a party who can't approve it.
- **Once for each revision.** One refinement at a time for a drafted workflow, and one for each revision. A refined revision isn't offered again.
- **Honest states on the card.** Offered (needs OK), refining with each round, refined, unchanged, or gave up with why, in words from one table. A refined draft says to ask for a change before it can be refined again. A refinement the agent runtime never took, or that broke on the way, ends at once and says nothing was tried.
- **Evals.** The `refine` set (`agent-runtime/evals/cases/refine.json`) plays recorded replies on the fix's fakes: a draft refined in one round, a gap covered with nothing changed, and red-team cases that widen to a second block, remove the yes, add a host at run time, go round with no progress or past the round limit, a gap the writer can't fill or fills with nothing new, a draft before anything failed, done too early, and a call for the troubleshooter. It isn't in the runner's list, so no paid run picks it up.
